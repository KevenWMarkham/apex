APEX-M · Architecture Brief · Merch Agentic Client

Building the Full Merch Suite on APEX-M

Buy · Plan · Allocate · Price · Replenish · Promote · Item · Supplier · Compliance

A strict superset of the Vuori WBR pattern. APEX-M sits alongside the merch systems, reading their outputs through the medallion and producing exception, recommendation, and decision artefacts back. Nine subject-area MCP servers · ten-to-fourteen named personas · ~70 use cases · ~24 sprints across three waves. The medallion shape, OIDC federation, five substrates, fifteen PSG gates, and LEDGER + Purview audit are unchanged from the Vuori build.

MCPs · 9 subject-area + 1 external signal Personas · 10–14 UCs · ~70 + 3 cross-domain journeys Sprints · ~24 (2 squads) Stays the same · medallion · OIDC · PSG · LEDGER

01The Merch Suite Landscape

The starting point — the canonical merchandising-systems landscape. Upstream systems feed the merch domain; downstream consumers receive the decisions. Nine capability boxes inside the merch envelope: six on the line (Buy / Plan / Allocate / Price / Replenish / Promote) and three masters underneath (Item / Supplier / Compliance).

02The APEX-M Overlay

APEX-M sits alongside the merch systems, not on top of them. Every system stays in place. The medallion lifts upstream + merch data into a substrate-blind shape; nine MCP servers expose typed tools per domain; the agent fleet composes those tools per the Microsoft Agent Framework patterns; HITL gates pause every Tier-2+ decision; LEDGER + Purview anchor the audit.

Augmentation, not replacement

The merch systems stay. Anaplan still owns planning; Centric still owns PLM; the allocation engine still allocates. APEX-M reads their outputs, finds the exceptions, proposes the next action, and routes it back into those systems through their existing inputs (planning push-back, allocation override, markdown trigger). This is the same posture the Vuori WBR build uses; it just scales horizontally.

03Nine MCP Servers · One Per Merch System

SQL stays inside the MCP server. Agents see only typed tools. Each MCP authenticates Entra Agent IDs; Tier-3 PII unlocks (vendor contact info, labor certifications, customer-level joins) require an explicit consent ticket and audit on every hit.

08What Stays Identical

The architectural backbone is unchanged. Every Wave-3 capability rides the same substrate as the Wave-1 stub.

  • Medallion shape — RAW / CLEANSED / CURATED, dbt-owned lifts, dual-calendar reconciliation, MAC-as-margin proxy.
  • OIDC federation + 5 substrates — laptop → dev → test → stage → prod with the same per-substrate Entra apps and Key Vault scopes.
  • PSG-1..15 deploy gates — every gate applies unchanged; PSG-15 just resolves more persona bindings.
  • LEDGER hash chain + Purview echo — audit substrate scales linearly with the number of personas.
  • MCP authentication via Entra Agent ID — same bearer-token pattern; compml-mcp is the heaviest user of Tier-3 consent tickets.
  • Test harness — same mvp_test_harness shape; manifest swap pattern (generic-apparel-retailer.yaml → <client>.yaml) unchanged.
  • Wizard + apex.py entry point — python apex.py launch drives the wizard against any substrate.

10Folding This Into the Book — Three Options

If this becomes a permanent artefact, here are three places it can live in the Library. The decision shapes how future engagements consume the reference.

Option 1

New Part VI in the Vuori Implementation Guide

Professional-APEX-M-Implementation-Guide-(Vuori-Example).html

Add three chapters: Buy-Plan-Price loop · Allocate-Replen-Comply · The Coordinator + Magentic. Keeps the engagement-scoped tone; the Vuori book becomes the canonical narrative across the full suite.

Trade-off: conflates a worked example with reusable architecture. Vuori book grows past 7,000 lines.

Option 2

A second Companion volume in the Library

Professional-APEX-M-Implementation-Guide-(Merch-Suite-Reference).html

Generic across clients. The architecture in this brief becomes its own runnable reference companion — fork-able by future engagements (Kohl's, REI, etc.). Keeps the Vuori book engagement-pure.

Best fit · preserves the Trilogy + Companions structure introduced in the Library landing.

Option 3

New chapter in the Services Guide (Volume II)

Professional-APEX-M-Services-Guide.html

Keeps the Trilogy doctrine + Companion case-study split intact. The merch-suite reference architecture lives in the doctrine volume; individual client examples remain in Companions.

Trade-off: the Services Guide is generic across all 38 services. A merch-specific chapter sits unevenly next to e.g. HLS or TMT chapters.

Recommendation

Option 2. The Library already accommodates Companions (the Vuori Implementation Guide is one). Adding a generic Merch-Suite-Reference Companion lets future merch engagements fork from a canonical architecture without disturbing the Trilogy doctrine or the Vuori engagement narrative. When a new client like REI or Kohl's commissions an engagement, their team clones the reference Companion to Professional-APEX-M-Implementation-Guide-(REI-Example).html and edits the specifics — the same pattern the Vuori engagement followed.
