How to Use This Book

What APEX Is — read this first

APEX is a framework that accelerates the building of services and agents on the Microsoft Platform. It is the architectural substrate Deloitte's Microsoft practice uses internally to deliver Services faster, more consistently, and with more rigorous governance. APEX is not a product and is not sold to clients. What clients buy are Services — productized envelopes from the 38-Service catalog (RC-E2E-03 · HLS-E2E-04 · TMT-TEL-RAA-04 · etc.), each with a KPI commitment and a two-contract Independence-compliant commercial structure (client ↔ Microsoft for platform · client ↔ Deloitte for the Service-delivery engagement).

What this means for deployment leads: the three-layer cake (Platform · Service · Agent) — the organizing idea below — is the framework's deployment topology. The Platform layer is the per-tenant Microsoft platform substrate Deloitte stands up under the framework's Bicep templates. The Service layer is the productized envelope the client contracted for; this is what gets deployed into the client tenant. The Agent layer is the reusable image set the framework promotes through the two-Container-Registry mirror. What's deployed in client tenants are Services and the agents that compose them, on the Microsoft Platform, accelerated by the APEX framework. When this book talks about "deploying APEX," read "deploying a Service that the framework built." The framework is the means; the Service is what's contracted for and what runs in the tenant.

This is the operator's companion to the Professional APEX Sellers Guide. Where the Sellers Guide answers how to position APEX-accelerated Services, this volume answers how to deploy them on the Microsoft Platform. It exists because, between a working laptop demo and a multi-tenant production rollout, there is a long list of questions that sellers, architects, and delivery leads keep asking — and a stable set of answers we have been refining since the MVP shipped.

The book is built around one organizing idea: the APEX framework deploys Services in three layers — Platform, Service, and Agent — and each layer has its own lifecycle, its own container registry, its own Bicep module set, and its own promotion path. If you keep the layers straight, the rest of deployment becomes routine. If you blur them, every onboarding becomes bespoke and every upgrade becomes risky. The whole book is a long argument for keeping the layers straight.

0.1 The Bottleneck Is No Longer the Agent

Two years ago the question was "can an LLM-driven agent reliably make a markdown decision a category manager will trust?" That question is now answered. The Sellers Guide documents the KPI envelope: Gross Margin +3.2pp, days-on-hand −28%, markdown-to-clear ratio +41%, $142K in margin protected per cold-chain excursion event, decision-loop time compressed from 5.7 hours to under 90 seconds with audit attribution. These are not laboratory numbers; they were earned in the W2 pilots that fed the MVP.

The bottleneck moved. Sellers can show a working agent on a laptop in twelve minutes. What they cannot show, easily, is the path from that laptop to a client's Azure tenant under a two-contract commercial model with cosign-signed images, customer-managed keys, an immutable audit ledger, and a Bicep deployment that another delivery team can run end-to-end in a different tenant next month. That is what this book is about.

0.2 The MVP Is a Reusable Asset, Not a Pilot

The Q1 MVP — built across six sprints in the Consumer/Merch/MVP repository — was scoped deliberately around RC-E2E-03 (Pricing & Revenue Decision Service). One service, two scenarios (cold-chain excursion, dynamic markdown), five agents (The Analyst, The Demand Checker, The Finance Lead, The Operations Lead, The Briefer), one substrate that runs on Docker Desktop on a delivery lead's laptop and on Azure Container Apps in the Lab. That is the smallest closed loop that proves the entire deployment motion.

The reason it was scoped that way is that everything in the MVP — the Bicep modules, the agent base image, the LEDGER hash chain, the test harness, the topology UX — is engineered to generalize. RC-E2E-03 is the test driver for an asset that is supposed to accelerate every subsequent service, from RC-E2E-04 (Loyalty churn) through TMT-TEL-RAA-04 (Monthly revenue assurance variance close). Appendix E lists all 38.

Note

If you ever hear "the MVP is just for retail" or "we'll rebuild this for healthcare," push back. The agent images, the Platform Bicep, and the LEDGER are industry-neutral. The schemas, fixtures, and KPI definitions per Service are what change. The asset is reusable; the Service is what gets reskinned.

0.3 The Three Operational Truths

Every chapter in this book is downstream of three operational truths. State them out loud once a week and you will avoid most of the deployment errors we have seen.

  1. Three layers, three lifecycles. Platform, Service, and Agent each have their own version, their own container registry, their own deployment cadence. Mixing them collapses lifecycles into a single brittle pipeline. Keeping them apart is the entire point of Chapters 1 and 12.
  2. Same image, two substrates. The container image that runs on a delivery lead's Docker Desktop is the same image that runs in Azure Container Apps. Substrate awareness lives at the edges — environment variables and Bicep parameters — not inside the agent code. Chapter 2 makes this concrete.
  3. Independence is structural, not stylistic. "DMTSP," "Microsoft platform capabilities," and "Microsoft-native deployment" are not preferences; they reflect a two-contract commercial model that the deployment architecture must enforce. Chapter 3 connects the language to the wiring.

0.4 What This Book Is Not

This is a deployment book. It is not:

  • A commercial book — that is the Sellers Guide. The KPI envelopes, ECIF eligibility, and Wave model live there.
  • An agent-design book — agent prompts, MCP tool catalogs, and persona briefs live in the Agentic-Merch component architecture and the runner-level documentation.
  • A data book — bronze/silver/gold schemas and the SCML/MERML/PROML data models are documented in the Data & Platform reference.

If you find yourself asking "what does this Service sell?" you want the Sellers Guide. If you are asking "how does this Service deploy?" you are in the right book.

0.5 Zero-Cost Development as a Design Goal

The fourth operational truth — a corollary to the three in §0.3 — is a design goal: the developer's inner loop runs at zero Azure cost. A new developer should be able to clone the repository, run docker compose up, exercise the entire MVP — agents, orchestration, LEDGER, harness, topology UX — and ship a working change without ever provisioning an Azure subscription or burning a dollar of consumption.

This is not a cost-optimization story; it is a structural choice that shapes substrate selection. Every laptop-tier component is free, open-source, and self-hostable in docker-compose:

  • Database — Azure Database for PostgreSQL on Azure → Postgres container locally (free).
  • Orchestration — Azure Logic Apps on Azure → n8n container locally (free, self-hosted under n8n's Sustainable Use License).
  • Agent runtime — Microsoft.App/containerApps on Azure → docker-compose locally (free).
  • Identity — Microsoft Entra ID on Azure → no-op stub locally (free).
  • Secrets — Microsoft.KeyVault on Azure → .env with synthetic fixtures locally (free).
  • Observability — Azure Monitor on Azure → stdout / file logs locally (free).

The first time a developer needs to think about cost is at the DEV (Lab v0.1) substrate transition, not during dev-loop iteration. The orchestration substrate parity in §2.6 — n8n on laptop, Azure Logic Apps on Azure — is the most consequential of these choices because it preserves zero-cost dev and Microsoft-platform-native production.

Best Practice — Preserve the zero-cost loop

If a new dependency would force the laptop tier to require an Azure subscription, treat it as a structural change. Push the dependency to DEV+ substrates and stub it on laptop. The zero-cost guarantee is what makes the MVP a frictionless reusable asset; protect it.

1.2 Why Three and Not Two

It is tempting to merge Service and Platform into one "deployment unit." That works at exactly one Service per tenant. The moment a tenant runs both RC-E2E-03 (Pricing & Revenue) and RC-E2E-04 (Loyalty churn), they share Platform but not Service. The Container Apps Environment, container registry, Key Vault, and Log Analytics workspace are common; the agents, the audit-row schema specialization, and the commercial envelope are per-Service.

It is equally tempting to merge Agent into Service — to think of "the RC-E2E-03 agent stack" as the unit. That breaks reuse. The Analyst appears in RC-E2E-03 (severity-rank cold-chain excursions), in HLS-E2E-04 (severity-rank prior-auth queues), and in TH-AIR-02 (severity-rank IROPS re-accommodations). One container image, three Services, three different fixtures and prompts. If the image is owned by the Service, you build three. If it is owned by Layer 3, you build one and parameterize.

Best Practice

When you draw a deployment diagram, draw three columns labeled Platform, Service, Agent and place every component in exactly one column. If a component is in two columns, you have a layer-violation; refactor before you write Bicep.

1.3 The Three Layers, Concretely

1.3.1 Layer 1 — APEX Platform

Stood up once per tenant. The Sprint 1 Bicep modules in MVP/agentic-merch/bicep/modules/ are the canonical implementation:

BICEP — modules
acr.bicep            // Premium container registry · Notary content trust · runtime AcrPull role
identity.bicep       // 4 user-assigned MIs (runtime, mcp, ingest, pii-unlock)
keyvault.bicep       // Premium HSM · CMK key (RSA-HSM 2048) · runtime + MCP role assignments
observability.bicep  // Log Analytics workspace + App Insights bound by WorkspaceResourceId
agents.bicep         // Container Apps environment (Consumption profile · KEDA)

main.bicep imports those five modules and parameterizes location (default centralus) and deploymentSuffix (default lab01). Outputs are runtimeIdentityId, keyvaultUri, acrLoginServer, and containerAppsEnvId — these are the inputs every Service consumes.

1.3.2 Layer 2 — Service

A Service is a Bicep module set that composes Container Apps onto the Platform's Container Apps Environment, plus per-Service configuration, secrets, and audit-row schema. RC-E2E-03 in Sprint 1 contributes the first Container App definition (agents.bicep includes The Analyst); Sprints 2–5 add the four remaining agents to the same Service. Sprint 6 packages all five into the Lab v0.1 deployment.

By Sprint 6 the Service-level Bicep parameter list looks like this:

BICEP — service params (rc-e2e-03)
param serviceCode string = 'rc-e2e-03'
param serviceVersion string = '1.0.0'
param containerAppsEnvId string  // from Platform output
param runtimeIdentityId string   // from Platform output
param acrLoginServer string      // from Platform output
param keyvaultUri string         // from Platform output
param agentImages object = {
  'the-analyst':         'agent-the-analyst@sha256:...'
  'the-demand-checker':  'agent-the-demand-checker@sha256:...'
  'the-finance-lead':    'agent-the-finance-lead@sha256:...'
  'the-operations-lead': 'agent-the-operations-lead@sha256:...'
  'the-briefer':         'agent-the-briefer@sha256:...'
}

Note that agent images are referenced by SHA digest, not by tag. This is a deliberate Layer-3-to-Layer-2 binding: a Service deployment locks to immutable image content, so a Layer 3 retag cannot silently change Service behavior. Chapter 12 explains the SemVer line for each layer and the compatibility matrix that pins them together.

1.3.3 Layer 3 — Agent

An Agent is a container image. It has a /run endpoint and a /healthz endpoint, both built by build_agent_app(runner=..., agent_id=...) in agentic_merch.base. The runner is the Service-specific behavior; the framework is shared.

PYTHON — agent image entry point
from agentic_merch.base import build_agent_app
from agentic_merch.the_analyst.runner import AnalystRunner

app = build_agent_app(runner=AnalystRunner(), agent_id="the-analyst")

The same image runs unchanged on Docker Desktop (via docker-compose.yml) and on Azure Container Apps (via the Bicep Container App resource). Substrate-awareness is environment-variable-driven and is the entire subject of Chapter 2.

1.4 Two Container Registries, One Path

Layer 3 images flow through two Azure Container Registry instances (Microsoft's Microsoft.ContainerRegistry/registries resource — see the note in How to Use This Book for the abbreviation collision):

  1. Deloitte authoring registry — apex-acr.azurecr.io, owned by the Deloitte engineering team. Builds, scans, and signs all agent images. Premium tier with Notary content trust and cosign verification on push. Source of truth for Layer 3 versions.
  2. Client tenant registry — per client Azure tenant, deployed by Layer 1's acr.bicep. Geo-replicated; receives images mirrored from the Deloitte authoring registry by the client's CI subscription. Cosign signature is verified on pull; an unsigned image cannot start.

The Service's Bicep references the client container registry. The Service never reaches into the Deloitte authoring registry at runtime; that boundary is one of the structural enforcements of the two-contract commercial model. Chapter 11 walks the promotion pipeline.

Warning

Do not let a delivery team pull agent images directly from the Deloitte authoring registry into a client tenant. It works on day one and breaks every audit on day ninety. The mirror is not a convenience layer; it is the boundary between Deloitte-built artifacts and client-deployed runtime.

Deloitte authoring (synthetic fixtures only) Client Azure tenant (per client) Mirror crossing (the only path) Forbidden — direct runtime access

2.1 The Promise: Same Image, Two Substrates

The container image that The Analyst ships in is the same image that runs on a delivery lead's Docker Desktop and the same image that runs on Azure Container Apps in the Lab. That promise — same image, two substrates — has two consequences.

  1. Every difference between substrates lives at the edges: environment variables consumed by the agent, secrets resolved at startup, ports bound by the substrate orchestrator. Inside the agent code, there are no if substrate == "azure" branches.
  2. The substrate orchestration layer — docker-compose.yml on a laptop, Bicep on Azure — is the only thing that changes when you move. The Bicep treats the image's environment as a translation target for what compose already provided.

If you find substrate logic inside the agent runner code, that is a layer violation. Push it out to the entry-point or to the Bicep / compose layer.

Independence — Substrate Tiers

The Lab tier (DEV) lives in a Deloitte-administered Azure subscription with synthetic fixtures only. STAGE and PROD live in client subscriptions; Deloitte deploys into client tenants under the Microsoft-platform contract for that client. Lab artifacts never see client data. Client artifacts never run in the Deloitte authoring tenant. This separation is structural, not operational; it is enforced by the container registry boundary in Chapter 1.

2.3 What Changes Between Substrates

Three things change as you move from laptop to Azure:

2.3.1 Configuration source

On a laptop, configuration comes from .env files referenced by docker-compose.yml. On Azure, configuration comes from Container App env vars and Key Vault references resolved at startup.

YAML — laptop
# MVP/docker-compose.yml
services:
  agent-the-analyst:
    image: agent-the-analyst:dev
    environment:
      AGENT_ID: the-analyst
      LEDGER_BACKEND: postgres
      LEDGER_DSN: postgres://harness:harness@postgres:5432/harness
      MCP_ENDPOINT: http://harness:8080/mcp
BICEP — Azure
// agents.bicep — Container App env block (excerpt)

  { name: 'AGENT_ID', value: 'the-analyst' }
  { name: 'LEDGER_BACKEND', value: 'postgres' }
  { name: 'LEDGER_DSN', secretRef: 'ledger-dsn' }

The image consumes the same env-var names. The substrate decides where those names get their values.

2.3.2 Secret resolution

On laptop, secrets are inline strings in .env (acceptable for synthetic fixtures only). On Azure, secrets resolve through Key Vault references attached to the runtime managed identity. The agent code does not know which it is using; it asks the substrate for the value of LEDGER_DSN and gets a string.

2.3.3 Networking and identity

On laptop, the compose network is flat; everything reaches everything by service name. On Azure, the Container Apps Environment provides DNS scoped to the env, ingress is internal-only by default, and any cross-Service traffic flows through the Environment's HTTP routing. Identity moves from "I trust the laptop user" to "I trust the user-assigned managed identity attached to the Container App."

2.4 What Does Not Change

The list of things that do not change is short and load-bearing:

  • The container image bytes. Same SHA on laptop and Azure.
  • The agent's HTTP contract. POST /run with the canonical request body produces the same response shape against the same fixture, on either substrate.
  • The LEDGER row schema. _hash and _prev_hash columns are written identically on laptop Postgres and on Azure Postgres-flavored backends; the chain verifies across substrates.
  • The audit-row attribution. The same cost_per_decision and safety_verdict fields are populated.

This invariance is what makes the test harness portable. The same UC catalog runs against laptop or Azure substrate by changing the harness's target endpoint. The harness does not care; the agent does not care; only the Bicep / compose orchestration knows.

Best Practice

When you add a new env var to an agent, add it to three places in the same merge: the agent's runner that reads it; docker-compose.yml; and the Bicep env: block. If you cannot do all three in one PR, the env var's substrate contract is not yet stable.

2.5 The W1→W2→W3 Commitment, Operationally

The Sellers Guide describes Wave 1, 2, and 3 commercially. Operationally, the commitment is simpler: moving up a wave extends the component graph; it never redraws it. A W2 pilot adds DAG orchestration, agents 1–3, and HITL gates on top of W1's bronze/silver/canonical pipeline; a W3 scale-and-fuse extends with enterprise-scale fuses and a feedback loop. The same applies to substrates: STAGE adds components to DEV; PROD adds components to STAGE.

The practical consequence: when a delivery team asks "do we need to rebuild the Bicep when we move from Lab to client tenant?", the answer is "no — you parameterize the Bicep by tenant and substrate suffix, and the same modules deploy with different inputs." Chapter 13 walks the day-zero onboarding that makes this concrete.

2.6.1 Why n8n on the laptop

n8n was chosen for laptop dev for four reasons:

  • Free and self-hostable. Preserves the §0.5 zero-cost dev guarantee. The n8n Docker image runs in compose with one volume for workflow JSON.
  • Visual node graph. Matches the n8n-style topology UX we use elsewhere in the MVP — the developer sees the same orchestration shape they will deploy to Logic Apps.
  • HTTP-first. n8n's HTTP node calls Container /run endpoints over the docker-compose network with no auth ceremony — exactly mirroring how Logic Apps will call Container Apps internal ingress on Azure.
  • Workflow JSON portability. n8n exports workflows as JSON; conversion to a Logic Apps workflow definition is a translation, not a rewrite. §2.6.3 covers the parity rule.

2.6.2 Why Azure Logic Apps on the Microsoft platform

On Azure, the orchestrator is Microsoft-native because the rest of Layer 1 is:

  • Managed identity binding. A Logic App authenticates as the Layer 1 mi-apex-merch-runtime user-assigned managed identity — no API keys, no client secrets.
  • Microsoft.KeyVault native connector. Secrets resolve through the Logic Apps Key Vault connector against the Layer 1 vault.
  • Microsoft Sentinel correlation. Logic App run history lands in the same Microsoft.OperationalInsights/workspaces as the agent traces; Sentinel rules correlate orchestrator decisions with agent behavior.
  • Microsoft Entra ID conditional access. The same conditional-access policy that protects the agents protects the Logic App.
  • Microsoft Cost Management attribution. Logic App cost flows under the same apex:service-code tag as the agents it orchestrates.

3.1 The Two-Contract Model

Independence is the rule that Deloitte's audit relationships with certain clients constrain the way Deloitte and Microsoft can co-sell and co-deliver to those clients. The operational consequence — the only one a deployment architect needs to internalize — is the two-contract model:

  • Contract 1. Client ↔ Microsoft, for the platform. Azure subscription, container registry consumption, Container Apps, Key Vault HSM. ECIF (if any) flows under this contract, direct from Microsoft to the client.
  • Contract 2. Client ↔ Deloitte, for services. Agent images, Service envelope, runbook delivery, support. Paid for by client out of separately negotiated SOWs.

The two contracts must not become one. ECIF must not flow through Deloitte. Co-marketing must not present Deloitte as a Microsoft "partner" or "alliance." This chapter covers what that looks like in Bicep, container registry, and runbooks.

3.3 Architectural Enforcement of the Two Contracts

Independence is not enforced by intent; it is enforced by where artifacts live and whose subscription pays for what.

3.3.1 Container registry boundary

The Deloitte authoring registry is in a Deloitte subscription. The client tenant registry is in the client subscription. Image bytes flow Deloitte → client by mirror + cosign verify. Client deployments pull only from the client registry. There is no path at runtime from a client Container App to the Deloitte authoring registry.

3.3.2 Subscription boundary

Layer 1 Bicep deploys into a client subscription. The Deloitte authoring tenant only ever holds reference deployments (Lab v0.1) with synthetic fixtures. Lab tenants and client tenants share zero data plane; they share only the agent image bytes that flow through the container registry boundary.

3.3.3 ECIF flow

If ECIF (Microsoft's Enterprise Customer Investment Funds) is in play, it flows directly from Microsoft to the client. Deloitte does not invoice the client for Microsoft platform consumption; Microsoft does. Deloitte SOWs are for services only. Bicep has no role in ECIF, but ECIF affects which subscription owns which resource — and that affects which managed identity owns which artifact.

Independence — Bicep parameter naming

When parameterizing tenant-specific Bicep, use names that reflect the boundary: clientTenantId, clientSubscriptionId, clientResourceGroup. Do not name parameters deloittePartnerTenant or jointDeploymentSub. The parameter names are part of the artifact's permanent record.

3.4 What This Means for Day-Zero Onboarding

The deployment motion in Chapter 13 begins with the client provisioning the Azure subscription and granting Deloitte's deployment principal a scoped role to deploy Bicep. The Deloitte principal does not own the subscription; it has a delegated permission set that lets it run az deployment sub create against the client subscription for the duration of the engagement. That is the Independence-compatible deployment posture.

Concretely, Chapter 13's onboarding checklist starts with five client-side actions before any Deloitte action runs. Appendix B has the full list. If you cannot tick those five client-side boxes before running Bicep, the onboarding is not yet structurally Independence-compatible and must not proceed.

3.5 The Five Things to Remember

  1. Two contracts. Microsoft for platform, Deloitte for services. Always two, never one.
  2. ECIF direct, never through Deloitte. The Bicep does not see ECIF; the SOW does.
  3. Two container registries. Deloitte builds and signs; client pulls verified images.
  4. "DMTSP" / "Microsoft-native deployment" / "Microsoft platform capabilities" — never "partner," "alliance," "strategic alliance."
  5. Lab and client tenants share images, never data.

Key Takeaways

  • Independence is enforced architecturally — by the container registry boundary, the subscription boundary, and the ECIF flow path — not just stylistically.
  • Two contracts: Microsoft for platform, Deloitte for services. ECIF flows direct.

5.1 Microsoft Entra ID — The Identity Boundary

Every runtime call inside a Layer 2 Container App authenticates as a user-assigned managed identity issued by Microsoft Entra ID. There are no client secrets, no service-principal passwords, no federated credentials wired into images. The four identities from §4.3 are the only ways a Container App can call Microsoft.ContainerRegistry, Microsoft.KeyVault, Azure Storage, Microsoft Fabric, or any other Microsoft platform resource.

The Microsoft Entra ID token issued to a user-assigned identity is short-lived (default 1 hour). Containers re-authenticate transparently via the IMDS endpoint at 169.254.169.254 — a Microsoft platform contract documented in the Container Apps managed-identity guide. The agent code does not handle token acquisition; the Microsoft Entra ID SDK in azure-identity (or the language-equivalent) handles it.

5.1.1 Microsoft Entra Agent ID — Agent-Native Identity (GA April 2026)

The four user-assigned managed identities in §4.3 cover resource access — they let a Container App reach Microsoft.ContainerRegistry, Microsoft.KeyVault, Microsoft Fabric, and the rest of the Microsoft platform. They do not, however, give an APEX agent its own identity for purposes of governance, conditional access, or agent-to-agent (A2A) authentication. Until April 2026, that gap was bridged with bespoke per-UAMI Conditional Access policies and ad-hoc OAuth dances.

Microsoft Entra Agent ID closes that gap. Per the Microsoft Learn overview, "Microsoft Entra Agent ID is an identity and security framework that extends Microsoft Entra capabilities to AI agents… The Microsoft Entra Agent identity platform enables developers to create and manage agent identities, which are specialized identity constructs built for AI agents. Agent identity blueprints serve as templates for creating individual agent identities with parent-child relationships, enabling consistent security policies across large numbers of agents."

APEX-M adopts Entra Agent ID as the canonical identity layer for agents in production. The four UAMI identities from §4.3 stay — they remain how the Container App reaches Azure resources. Entra Agent ID sits above them, providing:

  • Blueprint-based provisioning — one parent blueprint per APEX-M tenant (apex-m-tenant-root), one per APEX service (apex-m-rc-e2e-03-blueprint, etc.), and concrete identities per agent role per scenario instantiated from the service blueprint.
  • Policy inheritance — Conditional Access, RBAC, and lifecycle rules attached at the parent blueprint propagate to every child identity. Disable a blueprint and every identity beneath it disables in one operation — critical for incident response and tenant decommissioning.
  • OAuth 2.0 + MCP + A2A — Entra Agent ID supports the standard agent protocols natively, including the on-behalf-of (OBO) flow that propagates an HITL approver's principal through the agent's API calls.
  • Identity governance integration — access reviews, lifecycle management, and orphan-detection apply to agent identities the same way they apply to user identities.

The naming convention is deterministic so the wizard, the audit row, the Microsoft Entra portal, and the Foundry hosted-agent registration all stay in sync (see docs/APEX - Design and Build/agent-identity-blueprints.md §3):

APEX-M agent identity naming
tenant root            : apex-m-tenant-root
service blueprint      : apex-m-{service-code-lowercase}-blueprint
agent identity         : apex-m:{service-code}:{scenario-id}:{role}

Provisioning happens via Microsoft Graph. As of GA, Entra Agent ID resources are not yet exposed as native ARM resource types; the apex-m/infra/bicep/platform/identity.bicep module provisions the four UAMI identities natively and runs a deployment script that calls Microsoft Graph (POST /agentIdentities/blueprints and POST /agentIdentities/blueprints/{id}/instances) for the blueprints. When Microsoft.Graph/agentIdentities resource types land, the deployment script will be replaced with native Bicep resources.

The APEX-Core protocol contract. APEX-Core defines an AgentIdentityProvider protocol (see packages/apex-core/src/apex_core/protocols/agent_identity.py). APEX-M's implementation is apex_m.identity_entra.AgentIdentityProviderEntra, wrapping the Microsoft Graph endpoints. The implementation is variant-isolated — when APEX-G or APEX-A ship, each provides its own concrete impl (Cloud IAM service-account impersonation for APEX-G; IAM Identity Center + STS AssumeRole for APEX-A) against the same protocol. Agent code that uses the protocol works unchanged across all three variants.

Workload Identity Federation for the laptop substrate. Per Chapter 2, the same agent image runs on Docker Desktop locally and Foundry Hosted Agents on Azure. Local substrate uses Workload Identity Federation instead of stored secrets — the federated credential file at $AZURE_FEDERATED_TOKEN_FILE is a child of apex-m-{service-code}-blueprint in Entra Agent ID. Token exchange happens against the Microsoft identity platform; no static credential lives on the laptop. This satisfies the Microsoft Cloud Security Benchmark v2 AI-7 control (no long-lived secrets in development environments).

Skipping a level (e.g., creating an agent identity directly without a service blueprint) is rejected by the deployment script and the wizard's render endpoint. 5.2 Secret Resolution via Microsoft.App secretRef

Secrets reach the Container App via two mechanisms, both Microsoft-native:

5.2.1 Microsoft.KeyVault references in Container App env

The Microsoft.App/containerApps resource exposes a secrets array, where each entry can pull from a Microsoft.KeyVault/vaults/secrets by URI under the runtime identity:

BICEP — Container App secret pull
secrets: [
  {
    name: 'ledger-dsn'
    keyVaultUrl: '${keyvaultUri}secrets/ledger-dsn'
    identity: runtimeIdentityId
  }
  {
    name: 'mcp-bootstrap-token'
    keyVaultUrl: '${keyvaultUri}secrets/mcp-bootstrap-token'
    identity: mcpIdentityId
  }
]

Each secret is resolved by the identity declared on the secret entry — runtime for the LEDGER DSN, MCP for the MCP bootstrap token. The identities are not interchangeable; the Microsoft.Authorization role assignments in §4.1 ensure each can only resolve secrets in its own scope.

5.2.2 Just-in-time PII unlock

The fourth identity — mi-apex-merch-pii-unlock — is intentionally not bound to the Container App at deployment time. It is acquired at runtime via Microsoft Entra ID's acquireTokenForUserAssignedIdentity only when an audit-attributed PII unwrap is required. The acquisition itself writes a LEDGER row before the unwrap fires.

Warning — Do not co-mount PII unlock

If you bind mi-apex-merch-pii-unlock as a standing identity on a Container App, every replica gets standing unwrap permission. The just-in-time pattern is the entire security argument for splitting it from mi-apex-merch-runtime. Confirm in agents.bicep that the Container App's identity: block lists only runtime + MCP, not PII unlock.

5.3 The LEDGER and the Microsoft.KeyVault HSM Anchor

The MVP's LEDGER is a WORM (write-once, read-many) audit table — every agent decision, every HITL approval, every harness step generates a row. Sprint 1 added two columns: _hash and _prev_hash, computed by compute_row_hash in mvp_test_harness.runtime.ledger. The chain is verified by verify_chain, which returns a ChainResult(ok, broken_at, message).

The Microsoft platform piece: the seed of the chain — and, in PROD, periodic checkpoint rows — are signed using the Layer 1 CMK in Microsoft.KeyVault. The CMK is HSM-backed (RSA-HSM 2048), so the audit chain inherits the FIPS 140-2 Level 3 trust posture of the Microsoft-validated HSM. A LEDGER tamper attempt that bypasses the application path still has to forge an HSM signature, which is cryptographically infeasible.

PYTHON — LEDGER signing call (sketch)
from azure.identity import DefaultAzureCredential
from azure.keyvault.keys.crypto import CryptographyClient, SignatureAlgorithm

credential = DefaultAzureCredential()  # picks up runtime managed identity
crypto = CryptographyClient(key_id=cmk_key_uri, credential=credential)
sig = crypto.sign(SignatureAlgorithm.rs256, checkpoint_hash_bytes)
# write checkpoint row with sig column populated

Microsoft.KeyVault rate-limits HSM signing aggressively (Premium tier: hundreds of ops/sec, not thousands). For this reason, the LEDGER signs checkpoints — typically every Nth row or every minute — not every row. The chain links each row to its predecessor; the checkpoints anchor the chain to HSM-backed truth.

5.4 Microsoft Defender for Cloud and Microsoft Defender for Containers

Microsoft Defender for Cloud should be enabled at subscription scope on the client tenant before any Layer 1 deployment. Specifically:

  • Microsoft Defender for Containers — scans Microsoft.ContainerRegistry images on push and on pull; flags vulnerabilities in the image and its base layers; integrates with the Notation trust pipeline.
  • Microsoft Defender for Key Vault — alerts on anomalous Key Vault operations (mass secret read, unusual unwrap patterns).
  • Microsoft Defender for App Service — covers Microsoft.App/containerApps as part of its 2025 expansion.

These do not appear in the Layer 1 Bicep because they are subscription-scope toggles, not resource-scope deployments. Appendix B's Day-Zero checklist starts with confirming Defender for Containers is enabled on the target subscription.

customEvents
| where name == "ledger.row.committed"
| where customDimensions.agent_id == "the-analyst"

          step_id=customDimensions.step_id,
          row_hash=customDimensions._hash,
          cost=todouble(customDimensions.cost_per_decision),
          safety=customDimensions.safety_verdict

| order by ts desc

8.2 Why SHA-Digest References, Not Tags

Microsoft.ContainerRegistry resolves both image:1.4.0 and image@sha256:6a4c... at pull time. The difference: a tag can be re-pointed to a different image on the registry side without the consumer's awareness, and a Container App revision will pick up the new bytes on its next replica scale-out. A digest cannot. Pinning by digest is the Microsoft-platform-native way to make a Layer 2 deployment record reflect the exact Layer 3 bytes that ran.

The promotion pipeline (Chapter 10 / Appendix D) writes the digest of the signed agent image into the Service Bicep parameter file when the agent is promoted to a Service. The parameter file is checked in. The audit trail of "which Service version ran which agent bytes" is git-replicable.

Warning — Tag drift

If you ever use image:latest in a Service Bicep, your Service deployment is not reproducible. The Container App revision is reproducible (the revision template is locked), but the next scale-out pulls whatever latest currently points to. This is a Microsoft.ContainerRegistry behavior, not a Container Apps bug — it is intentional, and SHA-digest pinning is the documented mitigation.

10.2 The Microsoft.ContainerRegistry Pipeline

An agent image traverses six stages, each a Microsoft platform action:

  1. Build — az acr build against the Deloitte authoring registry (apex-acr.azurecr.io). The build runs inside Microsoft.ContainerRegistry's task service; no laptop docker daemon required.
  2. Scan — Microsoft Defender for Containers auto-scans on push. Vulnerabilities above policy threshold block the next stage.
  3. Sign — Microsoft Notation (notation sign) and cosign (cosign sign) produce two signatures stored as ORAS artifacts alongside the image. Notation is Microsoft-native; cosign is included for cross-tool ecosystem compatibility.
  4. Verify — notation verify confirms the signature matches the trust policy. Unsigned images cannot proceed.
  5. Mirror — image bytes mirror to the client-tenant Microsoft.ContainerRegistry by Microsoft.ContainerRegistry's import API (az acr import). Signatures mirror as ORAS artifacts on the same call.
  6. Pull — Container App revision pulls by SHA digest, with notation verify at pull time. A signature mismatch or trust-policy violation prevents the replica from starting.
SHELL — pipeline invocation (Microsoft tooling)
# 1. Build
az acr build --registry apex-acr \
    --image agent-the-analyst:1.4.0 \
    --file the_analyst/Dockerfile .

# 2. Scan (auto by Microsoft Defender for Containers)
az security assessment show \
    --assessed-resource-id "/subscriptions/.../registries/apex-acr"

# 3. Sign (Microsoft Notation + cosign)
notation sign apex-acr.azurecr.io/agent-the-analyst:1.4.0 \
    --key apex-signing-key
cosign sign apex-acr.azurecr.io/agent-the-analyst:1.4.0

# 4. Verify
notation verify apex-acr.azurecr.io/agent-the-analyst:1.4.0

# 5. Mirror to client-tenant container registry
az acr import \
    --name apexacrlab01 \
    --source apex-acr.azurecr.io/agent-the-analyst:1.4.0

# 6. Pull is implicit (Container App revision triggers it)
Independence — The mirror is the boundary

The mirror in step 5 is the only artifact that crosses from the Deloitte authoring tenant to a client tenant. It carries image bytes + signatures, never source, never secrets, never client data. Audit reconstructions can show, for any client deployment, exactly which image digest was mirrored and when, signed by whom, scanned by which Microsoft Defender policy version. That paper trail is the structural proof of the two-contract model at the Layer 3 boundary.

10.3 The Trust Policy

Microsoft Notation reads its trust policy from a JSON document. A representative APEX trust policy:

JSON — notation trust policy
{
  "version": "1.0",
  "trustPolicies": [
    {
      "name": "apex-strict",
      "registryScopes": [ "apexacrlab01.azurecr.io/agent-*" ],
      "signatureVerification": {
        "level": "strict",
        "override": {}
      },
      "trustStores": [ "ca:apex-deloitte-authoring" ],
      "trustedIdentities": [ "x509.subject:CN=APEX Authoring,O=Deloitte" ]

"Strict" is non-negotiable. Any policy weaker than strict — for example, "permissive" with override allowed — opens a path to running unsigned bytes in a client tenant, which would void the audit narrative.

The agent reads them via the runtime managed identity. New Services do not require a new image — they require a new set of Key Vault secrets and a new Service Bicep that references them.

Best Practice — When to fork an image

If two Services need fundamentally different agent logic (not just different weights or prompts) — for example, an Analyst that scores by Markov chain vs an Analyst that scores by gradient-boosted trees — fork the image into agent-the-analyst-tree as a sibling Layer 3 artifact. Do not fork the image to change a config value.

12.3 The Attestation Trail

Microsoft Notation signatures and cosign attestations travel with each image as ORAS artifacts. The cosign attestation can carry arbitrary in-toto predicates; the APEX pipeline writes a predicate of type apex.deloitte/agent-attestation with:

  • Image SHA digest
  • Agent SemVer + git commit SHA of source
  • Platform-compatibility range
  • Microsoft Defender for Containers scan summary (assessment ID + result)
  • Build timestamp + Microsoft.ContainerRegistry task identifier

The Service Bicep deployment can verify the attestation at deploy time, refusing to bind an agent image whose attested platform-compatibility range does not include the current Layer 1 version. That makes Layer 1/2/3 compatibility an enforceable runtime check, not a documentation request.

13.2 Client-Side Prerequisites (Five Boxes That Must Tick First)

14.1 The Service Onboarding Loop

For any Service from Appendix E being added to a tenant whose Layer 1 is live:

  1. Confirm the Tenant Profile exists and Layer 1 version satisfies the Service's platform_compatible range.
  2. Mirror agent images the Service composes from the Deloitte authoring registry to the tenant container registry. Each az acr import brings bytes + Microsoft Notation signatures + cosign attestations.
  3. Materialize Service-scoped secrets — Microsoft.KeyVault/vaults/secrets entries with <service-code>-* prefix.
  4. Run Service Bicep what-if against the tenant subscription, parameterized by the Tenant Profile + agent SHA digests + Service version.
  5. Deploy Service Bicep on approval. Microsoft.App/containerApps come up; Microsoft.Storage / Microsoft.DocumentDB / Microsoft.Sql per-Service stores come up.
  6. Run the test harness against the deployed Service — UC catalog drives end-to-end validation through the deployed Microsoft.App/containerApps endpoints.
  7. Connect SOR (in PROD only) — the Service's bronze landing connects to the client's source-of-record systems via Microsoft Fabric mirroring or Microsoft.DataFactory pipelines.

14.2 The Test Harness as Acceptance Gate

The MVP test harness in MVP/TestHarness/ is a contract validator. It loads the UC catalog (TestHarness/catalog_seed/uc_catalog.json), and for each UC, runs a multi-step scenario against the Service's Container Apps. Each step writes to LEDGER; the harness verifies the chain at end of run.

For RC-E2E-03, the harness validates UCs that exercise:

  • The two scenarios in scope (cold-chain excursion, dynamic markdown).
  • The five-agent composition (every agent sees an inbound /run in some UC).
  • HITL approval loop — the Operations Lead's adaptive-card output survives a round-trip through the harness's HITL stub.
  • LEDGER hash chain integrity at end-of-UC.

If the harness reports any UC FAIL, the Service is not promoted. The harness gates the rollout regardless of whether the Bicep deployed successfully.

Best Practice — Harness against deployed Service

Run the harness against the freshly deployed Microsoft.App/containerApps endpoints, not against laptop containers. The whole point of the dual-substrate architecture is that the harness exercises the same behavior on either substrate; running against deployed Service catches Microsoft platform-specific issues (managed-identity auth, Microsoft.KeyVault secret resolution, Microsoft Notation pull-time verification) that laptop runs cannot.

Agent Upgrades Across Clients

What This Chapter Does for You
  • Walks the upgrade motion when a Layer 3 agent image needs to roll out across many Services and many tenants.
  • Maps the canary-and-promote pattern using Microsoft.App/containerApps revisions and traffic-split rules.
  • Establishes the CAB / approval cadence aligned to the three-layer SemVer.
TL;DR · 60 seconds
  • Agent upgrades are byte-level changes; what they trigger depends on patch / minor / major SemVer bump.
  • Within a tenant: Microsoft.App/containerApps revision-multi mode + traffic-split for canary 5% → 25% → 50% → 100%.
  • Cross-tenant rollout is a wave plan: Lab → STAGE → early-PROD → all-PROD; each wave gate produces an audit-replicable checkpoint.
  • Don't fan-out a digest to all tenants in one shot; per-tenant canary protects against tenant-specific regressions.

15.1 What "Agent Upgrade" Means at Each Layer

An agent upgrade is, at the byte level, a new SHA digest in the Deloitte authoring registry. What it triggers depends on whether the bump is patch, minor, or major:

  • Patch — prompt tweak, weight retune. Agents within compatible Service version ranges pick up the new digest on next mirror + revision rollover. No Service Bicep change.
  • Minor — new MCP tool dependency, new env var, backward-compatible behavior change. Service Bicep parameter file updates the SHA digest; the Service version may patch-bump.
  • Major — HTTP contract change at /run, LEDGER row schema change. Service version major or minor bumps; compatibility matrix updates; client-tenant rollout follows the upgrade window.

15.2 The Canary-and-Promote Pattern

Microsoft.App/containerApps supports multiple revisions per app with traffic-split rules. The standard canary pattern for an agent upgrade in a single tenant:

  1. Mirror the new agent SHA digest to the tenant container registry (az acr import).
  2. Update the Service Bicep parameter file with the new digest. Run Bicep with revision-mode set to multiple.
  3. The new revision deploys alongside the current revision. Traffic-split is set to 95% current / 5% new initially.
  4. Observe Microsoft.Insights for ~30 minutes. Compare cost-per-decision, safety-verdict distribution, LEDGER row counts between revisions.
  5. If healthy, ramp: 75/25 → 50/50 → 0/100. If unhealthy, snap back to 100/0 on previous revision.
  6. Once at 0/100 stable for 24 hours, retire the previous revision.
BICEP — traffic split for canary
configuration: {
  activeRevisionsMode: 'Multiple'
  ingress: {
    external: false
    targetPort: 8000
    transport: 'http'
    traffic: [
      { revisionName: '${appName}--rev1-4-0', weight: 95 }
      { revisionName: '${appName}--rev1-4-1', weight: 5,  latestRevision: false }
    ]
  }
}

15.3 Cross-Tenant Rollout

Across multiple client tenants, the same canary motion runs per tenant in waves. Typical wave plan for a Layer 3 minor upgrade:

  1. Wave 0 — Lab v0.1 (DEV). Full canary + observation. Pass criterion: 24 hours stable + harness PASS.
  2. Wave 1 — STAGE in 1–2 client tenants. Synthetic load + smoke harness.
  3. Wave 2 — PROD in early-adopter tenants. Canary + 72-hour observation per tenant.
  4. Wave 3 — PROD in remaining tenants. Standard canary; rollback playbook on file.

Each wave gate is a small CAB-equivalent — not a process for its own sake but a checkpoint the audit chain can later reconstruct ("on date X, version Y was promoted to wave Z based on observability evidence E").

Warning — Don't roll the same digest into all tenants in one shot

It is technically possible to mirror an agent image to all client tenant registrys at once and then redeploy Service Bicep across all tenants in parallel. It is not advisable. The first tenant catches issues that the laboratory could not — the canary-per-tenant cadence protects against tenant-specific regressions in Microsoft.KeyVault HSM region, Microsoft Defender policy version, or Microsoft Sentinel rule interaction.

Key Takeaways

  • Agent upgrades are byte-level changes; what they trigger depends on patch / minor / major SemVer bump.
  • Within a tenant, use Microsoft.App/containerApps revision-multi mode + traffic-split for canary 5% → 25% → 50% → 100%.
  • Cross-tenant rollout is a wave plan: Lab → STAGE → early-PROD → all-PROD; each wave gate produces an audit-replicable checkpoint.
  • Don't fan-out a digest to all tenants in one shot; per-tenant canary protects against tenant-specific regressions.

16.1 Rollback by Layer

The crucial property: rollback at any layer leaves the LEDGER intact. Audit chain rows about the failed upgrade are still in the chain; they are not deleted, only superseded by subsequent rows reverting the change. This is a Microsoft.Sql / Microsoft.DBforPostgreSQL behavior with append-only enforcement at the LEDGER table level — a structural rather than procedural guarantee.

16.2 What Cannot Be Rolled Back

  • Microsoft.KeyVault HSM key deletion — Layer 1 enables purge protection; the soft-deleted key recovers within 90 days. Past that, key material is unrecoverable. Operationally this means a CMK rotation must overlap with the prior key for at least 90 days before the prior key is purged.
  • LEDGER rows — WORM. Append only. Rollback produces a new row that supersedes; it does not erase.
  • Microsoft.ContainerRegistry image deletion — once a digest is removed from the registry and from any cached pull, the bytes are gone. Sprint 1's retention policy keeps 30 days of all images, plus indefinitely-retained signed-and-promoted versions.
  • Client-tenant data plane — STAGE/PROD bronze landing is the client's record; Deloitte does not own the rollback there.

16.4 The Reusable-Asset Discipline

The closing argument of the book: the deployment cost per client falls only if every artifact built for client N is reusable for client N+1. The MVP is the reusable asset; this guide is the discipline.

The discipline, in practice, is four habits:

  1. Resist client-specific Bicep forks. If a client requires a deviation, parameterize it. If parameterization is not possible, push the deviation into a Service-level module, never a Layer 1 module.
  2. Resist tag-pinning to latest. Every agent image reference is a SHA digest. Every. One.
  3. Resist re-implementing the harness per client. The UC catalog is generic. Client-specific scenarios extend it; they do not replace it.
  4. Resist out-of-band documentation. If a client deployment needs an instruction that is not in this book or its sources (deployment.md, the Service envelopes, Appendix E), update the source. The book is the operating manual; if it does not say something, the deployment cannot rely on it.

Each habit is unglamorous. Each habit, kept, makes the fortieth client deploy in a day what the first client took a quarter to deploy. That is the entire commercial story of why APEX is a reusable asset and not a custom build per engagement — and it is also the only durable reason a delivery team gets to use this book as a checklist instead of writing one from scratch.

Never partner, never alliance, never strategic alliance. The two-contract commercial structure — client ↔ Microsoft for platform, client ↔ Deloitte for services, ECIF direct — is enforced architecturally by the boundaries described in Chapter 1 (two container registries), Chapter 3 (subscription separation), and Chapter 13 (client-side prerequisites). Appendix I

Anti-Patterns & Pitfalls

The reusable-asset discipline (§16.4) lists four habits to keep. This appendix lists the inverse — the deployment mistakes we have actually seen break engagements, organized by where they typically occur. Each entry has a name (so teams can call it out by name during code review), a symptom, the signal that surfaces it, and the corrective action. The list is not exhaustive; contributing new entries by following the pattern is encouraged.

I.1 Layer-Mixing Anti-Patterns

Anti-pattern · "Service Bicep creates its own ACR"

Symptom: A Service Bicep module includes a Microsoft.ContainerRegistry/registries resource block instead of consuming the Layer 1 ACR via parameter input.

Signal: What-if shows a new ACR being created when deploying the Service. Cost report shows multiple ACRs in the same tenant.

Why it breaks: Image deduplication is lost across Services. Layer 3 image promotion has to mirror to N registries instead of one. Layer 1 amortization (§9.1) collapses; per-Service cost rises with N.

Fix: Remove the ACR block from the Service Bicep. Add acrLoginServer as an input parameter consuming the Layer 1 output. The Layer 1 ACR is the only ACR in the tenant.

Anti-pattern · "Service module duplicates managed identities"

Symptom: A Service Bicep creates new Microsoft.ManagedIdentity/userAssignedIdentities resources instead of consuming the Layer 1 four-identity set.

Signal: Microsoft Entra ID enterprise applications inflate with per-Service runtime/MCP/ingest identities. Conditional-access policies become unmanageable.

Why it breaks: The four-identity blast-radius split (§4.3) is undermined. Compromise containment becomes per-Service rather than per-function.

Fix: Remove the identity creation from the Service Bicep. Consume runtimeIdentityId, mcpIdentityId, etc. as parameters from the Tenant Profile.

Anti-pattern · "Per-tenant agent build"

Symptom: Agent images are built from source in each client tenant's CI pipeline rather than mirrored from the Deloitte authoring registry.

Signal: Tenant ACRs show az acr build task runs. Image SHA digests differ between tenants for the "same" agent version.

Why it breaks: The two-registry Independence boundary collapses (§1.4 · §3.3.1). Image bytes are no longer identical across tenants; cosign attestations don't propagate. Audit reproducibility ("what code ran on day X") fragments per tenant.

Fix: Build only in the Deloitte authoring registry. Mirror via az acr import. SHA digests must match across all tenant registries holding the same agent version.

I.2 Image-Reference Anti-Patterns

Anti-pattern · "Tag-pinned image reference"

Symptom: A Service Bicep references agent images by tag (e.g., agent-the-analyst:1.4.0) rather than by SHA digest.

Signal: Container Apps revision template shows image: ...:1.4.0 instead of image: ...@sha256:....

Why it breaks: Tags are mutable on the registry side. A re-tagged image will silently pick up new bytes on the next replica scale-out. The Service deployment's audit narrative ("this Bicep deployed these specific agent bytes on date X") becomes unprovable.

Fix: Always reference by digest. The promotion pipeline (Appendix D) writes the digest into the Service parameter file; the parameter file is checked in; the audit trail is git-replicable.

Anti-pattern · ":latest in production"

Symptom: Anywhere — Bicep, compose file, ARM template — a Container App pulls image:latest.

Signal: Grep for :latest in the deployment repo finds matches outside of explicitly laptop-only docker-compose files.

Why it breaks: Same as tag-pinning, but worse — there is no reproducibility at all. Container App revisions become time-of-day-dependent.

Fix: Block in CI. Reject any deployment artifact that contains :latest outside the laptop-tier compose file (where it's acceptable for dev convenience but not production).

I.3 Identity & Secrets Anti-Patterns

Anti-pattern · "API key in env var"

Symptom: A Container App has plain-text API keys, connection strings, or service-principal passwords in its env: block (rather than secretRef-resolved Microsoft.KeyVault references).

Signal: Bicep diff shows raw secret values; or a leaked credential scan finds keys in the deployment history.

Why it breaks: The whole identity model from Ch 5 is bypassed. Microsoft Entra ID conditional access doesn't apply. Compromise containment fails.

Fix: Move the secret to Microsoft.KeyVault. Reference by secretRef with the appropriate identity binding (runtime · MCP · pii-unlock per §5.2.1). Rotate the previously-exposed credential.

Anti-pattern · "PII unlock identity bound at deploy time"

Symptom: The mi-apex-merch-pii-unlock identity appears in a Container App's identity: block as a standing user-assigned identity.

Signal: Bicep grep finds piiUnlockIdentityId wired into a Container App resource definition.

Why it breaks: The just-in-time pattern from §5.2.2 is the entire security argument for splitting pii-unlock from runtime. Standing-bind gives every replica permanent unwrap permission.

Fix: Remove pii-unlock from the Container App's standing identity list. Acquire JIT via acquireTokenForUserAssignedIdentity at the HITL approval moment, with a LEDGER row written before the unwrap fires.

I.4 Network Anti-Patterns

Anti-pattern · "Public-network access in PROD"

Symptom: PROD Microsoft.ContainerRegistry, Microsoft.KeyVault, or Microsoft.Sql shows publicNetworkAccess: 'Enabled'.

Signal: Bicep audit run finds public access flags in PROD parameter files.

Why it breaks: The §6.2 STAGE/PROD posture (private endpoints + VNet integration + NSGs) collapses. Microsoft Defender for Cloud will flag it; Microsoft Sentinel UEBA will alert; the audit committee will note it.

Fix: Set publicNetworkAccess: 'Disabled' in PROD parameter files. Add private endpoints. Run the Bicep audit pre-commit hook to keep it from regressing.

I.5 Audit & Compliance Anti-Patterns

Anti-pattern · "LEDGER UPDATE/DELETE allowed"

Symptom: The LEDGER table in Azure SQL Database or Microsoft.DBforPostgreSQL Flexible Server allows UPDATE or DELETE operations from the runtime identity.

Signal: Database-level role grants show UPDATE/DELETE on LEDGER for non-break-glass identities.

Why it breaks: The append-only WORM enforcement (§16.2 · cross-ref Services Guide §25.2) is structural, not procedural. Without DB-level revocation, a runtime bug or compromised identity can rewrite history.

Fix: REVOKE UPDATE, DELETE ON LEDGER FROM <runtime_role>. Only a break-glass admin role retains UPDATE/DELETE; use of break-glass triggers Microsoft Sentinel UEBA alert.

Anti-pattern · "Tags missing on deployed resources"

Symptom: Microsoft Cost Management reports show resources without apex:service-code or apex:layer tags.

Signal: Cost-by-tag query returns "untagged" rollup > 5% of total spend.

Why it breaks: The W3 outcome-based commercial envelope requires per-Service cost attribution (§9.2 · cross-ref Services Guide Ch 29). Untagged resources break the Service P&L query.

Fix: Audit Bicep tag inheritance. Add apex:layer · apex:service-code · apex:tenant-suffix as mandatory tags in main.bicep and propagate to every tags: block. Re-tag deployed resources via az resource tag if needed.

I.6 Operational Anti-Patterns

Anti-pattern · "Skip-the-canary upgrade"

Symptom: An agent image upgrade is rolled to 100% traffic in a tenant immediately, without a 5%/25%/50% canary ramp (§15.2).

Signal: Container App revision history shows traffic split going from 100/0 on the prior revision directly to 0/100 on the new revision.

Why it breaks: Tenant-specific regressions (Microsoft.KeyVault HSM region differences, Microsoft Sentinel rule interaction, Microsoft Defender policy version mismatch) are caught only at the canary stage. Skip-the-canary masks regressions until they hit production traffic at scale.

Fix: Enforce the canary motion in the deployment pipeline. Block PRs that bypass traffic-split staging. Pair with golden-set + LLM-as-judge evaluation gates from Services Guide §28.5.

Anti-pattern · "All tenants in one shot"

Symptom: An agent image upgrade is mirrored to all client tenant ACRs at once and Service Bicep redeployed across all tenants in parallel.

Signal: Wave plan for the upgrade has fewer than three waves, or all waves complete within hours.

Why it breaks: Same as skip-the-canary, but at the cross-tenant scale. The first tenant catches issues that the laboratory could not — per-tenant canary protects against tenant-specific regressions in HSM region · Defender policy · Sentinel rule interaction.

Fix: Wave plan from §15.3 — Lab v0.1 (Wave 0) · STAGE in 1–2 client tenants (Wave 1) · PROD early-adopter tenants (Wave 2) · all PROD tenants (Wave 3). Each wave's pass criterion: 24-hour observation + harness PASS.

I.7 Independence Anti-Patterns

Anti-pattern · "Deloitte ACR pulled at runtime by client tenant"

Symptom: A client tenant Container App pulls images from apex-acr.azurecr.io (the Deloitte authoring registry) at runtime instead of from the per-tenant ACR.

Signal: Container App configuration shows registries: [{server: 'apex-acr.azurecr.io', ...}] in production.

Why it breaks: The structural enforcement of the two-contract model at Layer 3 (§1.4 · §3.3.1) is undone. Client deployments now have a runtime dependency on a Deloitte-owned subscription. Independence is performatively asserted but structurally broken.

Fix: All client Container Apps reference the per-tenant ACR. The Deloitte authoring ACR is reachable only by the mirror import path, never by runtime pull.

Anti-pattern · "Partner / alliance language in deployment artifacts"

Symptom: Bicep parameter descriptions, README files, runbooks, or operator-facing docs contain partner, alliance, or strategic alliance.

Signal: Regex grep across the delivery repo finds matches.

Why it breaks: The Independence posture (§3.2 · cross-ref Sellers Guide §6.13) is a contractual structure. Artifacts surviving the engagement that erode the language can be quoted back at procurement reviews three years later.

Fix: Pre-commit hook with the regex as a build-fail. Bulk replace existing matches with DMTSP · Microsoft platform capabilities · Microsoft-native deployment. Verify clean on every PR.

I.8 The Pre-Commit Hook (Recommended)

Most of these anti-patterns are catchable by automated pre-commit checks. Recommend wiring the following into the delivery repo's .git/hooks/pre-commit:

SHELL — pre-commit anti-pattern checks
#!/usr/bin/env bash
set -e

# 1. Block partner/alliance language
if git diff --cached | grep -iE 'partner|strategic alliance|alliance' > /dev/null; then
  echo "✗ Independence violation: partner/alliance language found"; exit 1
fi

# 2. Block :latest in non-laptop files
if git diff --cached --name-only | grep -v 'docker-compose' | xargs grep -l ':latest' 2>/dev/null; then
  echo "✗ Tag-pinning violation: :latest found outside laptop-tier compose"; exit 1
fi

# 3. Block public-network access in PROD parameter files
if git diff --cached --name-only | grep -E 'parameters/.*-prod\.bicepparam$' | xargs grep -l "publicNetworkAccess.*Enabled" 2>/dev/null; then
  echo "✗ Network-posture violation: PROD has publicNetworkAccess=Enabled"; exit 1
fi

# 4. Block secret values in env blocks (heuristic: long alphanumeric strings)
if git diff --cached -- '*.bicep' | grep -E "value:.*[A-Za-z0-9+/]{40,}" > /dev/null; then
  echo "✗ Secret-in-env warning: long string in Bicep env value · review for secrets"; exit 1
fi

echo "✓ Pre-commit anti-pattern checks passed"

Appendix G

Glossary

Azure Container Registry · Microsoft.ContainerRegistry/registries — Microsoft's managed OCI registry. Premium SKU is mandatory for APEX (geo-replication, content trust, CMK encryption, zone redundancy). Microsoft's CLI uses the abbreviation ACR (e.g., az acr build), but in Microsoft commercial contexts ACR also means Azure Consumption Revenue; this book spells the registry term out in prose to avoid the collision. CLI commands, the apex-acr.azurecr.io hostname, the acr.bicep module filename, and the AcrPull RBAC role name retain Microsoft's literal naming.

Application Insights · Microsoft.Insights/components — Workspace-based APM that emits to Microsoft.OperationalInsights. Connection string auto-injected into Microsoft.App/containerApps via the managed environment's daprAIConnectionString.

Azure Container Apps · Microsoft.App/containerApps — Managed serverless container runtime. Each agent in a Service is one Container App.

Azure Logic Apps — Microsoft platform workflow orchestrator. APEX uses Logic Apps Hybrid (Logic Apps Standard runtime hosted on Microsoft.App/containerApps with kind=workflowapp) as the default Azure orchestrator, with Logic Apps Standard on Microsoft.Web/sites and Microsoft.Logic/workflows Consumption available for niche cases. Substrate counterpart of n8n.

Bicep — The Microsoft platform IaC language. All APEX Platform and Service deployments are Bicep-defined.

CMK — Customer-Managed Key. APEX CMK is RSA-HSM 2048 in Microsoft.KeyVault Premium, providing FIPS 140-2 Level 3 root of trust for container registry encryption, Key Vault soft-delete recovery, and LEDGER checkpoint signing.

DAG Orchestrator — The orchestration role in the W2-pilot scenario chain ("Event Fires · DAG Orchestrator · Agent 1 · Agent 2 · Agent 3"). Realized by n8n on the laptop tier and by Azure Logic Apps Hybrid on the Microsoft platform.

Container Apps Environment · Microsoft.App/managedEnvironments — Layer 1 resource hosting all Container Apps in a tenant. Binds Log Analytics + Application Insights; declares workload profiles (Consumption, Dedicated D4).

Cosign — OCI image signing tool. Used alongside Microsoft Notation for cross-tool ecosystem compatibility.

DMTSP — Deloitte Microsoft Technology & Services Practice. The Independence-compliant phrasing for the Deloitte–Microsoft delivery relationship.

ECIF — Microsoft Enterprise Customer Investment Funds. Flows direct from Microsoft to client; never through Deloitte.

HITL — Human-in-the-loop. Operator approval gate within an agent decision flow.

HSM · Microsoft Hardware Security Module — Microsoft.KeyVault Premium-backed HSM module. RSA-HSM keys never leave the HSM in cleartext.

Independence — The audit-relationship rule constraining Deloitte–Microsoft co-delivery. Enforced architecturally in APEX via two contracts, two container registries, separated subscriptions, and disciplined language.

KEDA — Kubernetes Event-Driven Autoscaling. Built into Microsoft.App/managedEnvironments runtime; rules declared on Microsoft.App/containerApps.

KQL — Kusto Query Language. The query language for Microsoft.OperationalInsights and Application Insights.

LEDGER — APEX append-only audit table. Hash-chained (_hash, _prev_hash); checkpoint signing with the Microsoft.KeyVault HSM CMK.

Logic Apps Hybrid — Azure Logic Apps Standard runtime hosted on Microsoft.App/containerApps with kind=workflowapp. Default Azure orchestrator for APEX because it amortizes onto the same Layer 1 Container Apps Environment as the agents.

MCP — Model Context Protocol. The agent's tool-call interface. APEX MCP tool catalog is scoped per Service via the mi-apex-merch-mcp identity.

Microsoft Defender for Cloud / for Containers / for Key Vault / for App Service — Microsoft's cloud security posture management. APEX requires Defender for Containers for image scanning + runtime threat detection.

Microsoft Entra ID — Microsoft's identity provider (formerly Microsoft Entra ID). All APEX runtime authentication is via Microsoft Entra ID-issued user-assigned managed identity tokens.

Microsoft Fabric · Microsoft.Fabric/capacities — Unified analytics platform. Lakehouses host Gold serving for APEX Services.

Microsoft Notation — Microsoft's content-trust signing tool. Strict trust policies enforce signed-only image deployment.

Microsoft Purview · Microsoft.Purview/accounts — Catalog and lineage. APEX assets register with the tenant Purview account for audit-and-discoverability.

Microsoft Sentinel — Microsoft's SIEM/SOAR. Attached as a workspace solution on Layer 1's Log Analytics workspace; UEBA on the four user-assigned managed identities.

n8n — Open-source workflow automation. APEX uses self-hosted n8n in docker-compose as the laptop-tier orchestration substrate, preserving the §0.5 zero-cost dev guarantee. Substrate counterpart of Azure Logic Apps. Does not deploy to client tenants.

Notation trust policy — JSON document declaring registry scopes, trust stores, and verification level. APEX uses level "strict."

SemVer — Semantic versioning. Independent SemVer per layer: apex-platform, per-Service, per-agent.

Service — In this book, one of the 38 productized envelopes from Appendix E. The unit of deployment, commercial envelope, and audit attribution.

Substrate — The runtime environment for agents. APEX recognizes four substrate tiers: laptop (Docker Desktop), DEV (Lab v0.1 Azure), STAGE, PROD.

Tenant Profile — YAML artifact emitted at Day-Zero recording the Microsoft platform resource IDs and identifiers for a client tenant. Consumed by every subsequent Service onboarding.

Two-contract model — Independence-compliant commercial structure: client contracts Microsoft for platform, client contracts Deloitte separately for services. ECIF flows direct.

UC · Use Case — Test harness scenario. Each UC drives a multi-step exercise of a Service through deployed Microsoft.App/containerApps endpoints.

W1 · W2 · W3 — APEX Wave structure. W1 Foundation (4–8 weeks); W2 Pilot (6–15 months, Lab v0.1 → STAGE → first PROD tenant); W3 Scale & Fuse (multi-year, fortieth-tenant scale-out and cross-Service composition).

WORM — Write-once, read-many. The append-only enforcement applied to LEDGER tables in Microsoft.Sql or Microsoft.DBforPostgreSQL.

Workflow parity — The contract that every orchestration in APEX is maintained as a single conceptual flow with substrate-specific JSON for both n8n (laptop) and Azure Logic Apps (Microsoft platform). Repository layout: workflow.intent.md + workflow.n8n.json + workflow.logicapp.json. CI verifies the two stay in sync.

  • Native M365 Copilot orchestration (no APEX runtime intervention)
  • Automatic SharePoint / OneDrive grounding with sensitivity-label inheritance per Purview for Copilot Studio

APEX-M can publish a Declarative agent for the read-only lookup path while the Foundry-hosted Custom Engine Agent handles decision-making.
