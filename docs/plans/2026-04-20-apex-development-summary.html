APEX is Deloitte's delivery accelerator for agentic AI on Microsoft Fabric. Architectural invariants enforced across every sprint

Five-plane model

Every package aligns to exactly one plane: Data (Fabric), Reasoning (Foundry), Experience (Copilot), Trust (Purview), Identity (Entra). Cross-plane chatter flows through MCP tools, never through direct imports.

Four-layer manifest inheritance

L1 Contract (platform invariants) → L2 Edition (industry pack) → L3 Practice (e.g. RC, HLS) → L4 Tenant (client overrides). Every runtime decision resolves the stack → deepest valid override wins; auditor sees all four layers via resolve_decision().

Five-field canonical envelope

event_id, event_ts, entity_id, source_system, source_system_ts on every Bronze row — lineage, replay, and de-dup fall out for free.

Three-version rule

Every Decision Audit Row pins manifest_version + policy_version + prompt_version Git SHAs plus the Foundry model_version. The auditor can reconstruct any past decision without change-log reasoning.

Medallion as contract, not folders

Bronze / Silver / Gold are promotional contracts enforced by apex-medallion: schema drift quarantines to dead-letter; PII tokenises before Silver; Gold is Purview-registered with WORM retention.

Gates as first-class runtime

Four kinds (ZERO_TOUCH / ACK_ONLY / HITL / ESCALATION) x four variants (hard / soft / policy / escalation) resolved from SemVer bump class plus tenant override. Paused HITL survives process restart.

Implementation philosophy

Ship the contract, then ship the runtime. Every sprint delivered a frozen Pydantic model (the contract) before any side-effecting code. That way every downstream consumer — notebooks, MCP servers, Copilot plugins — negotiates against the same immutable shape. When Sprint 12 retrofitted ledger-mcp to enforce the 14-field AuditRow, the change touched one file because every other package was already talking the contract.

Determinism everywhere it costs nothing. Content hashes are json.dumps(..., sort_keys=True); tokens are HMAC'd with tenant|classification|value so the same plaintext under two labels mints two distinct tokens; SemVer bump class maps to gate kind by a pure function. No randomness, no wall-clock, no per-process state in the decision path — the only non-deterministic inputs are the Entra principal and the agent's reasoning.

Why APEX — the design case in four numbers

The APEX design document opens with the claim that Microsoft's stack is necessary but insufficient for production agentic AI in regulated industries. The design quantifies the gap across four independent design forces; every invariant downstream is traceable to one of them.

Force 1 — Auditability

EU AI Act Article 14 requires "appropriate human oversight" to be demonstrable per decision. SOX, HIPAA, GDPR, and FDA 21 CFR Part 11 impose similar structured-evidence requirements. An agent that emits a log line is not compliant; an agent that emits a signed, structured, Git-pinned audit row is. §1 Design forces; §11 Audit row

Force 2 — Reproducibility

Foundation models change under you. The same prompt against gpt-4o-2024-08 and gpt-4o-2024-11 gives different answers. APEX pins the exact model version, prompt SHA, and policy SHA on every row — so a 2026-Q4 auditor can still reconstruct a 2026-Q1 decision. Without three-version pinning, agentic AI is forensically opaque. §11.7 Three-version rule

Force 3 — Tenant isolation

A consulting accelerator runs N clients on the same codebase. Token collisions, classification leaks, or policy bleed across tenants are a career-ending incident. APEX composite-keys every governance artefact (tokens, rows, scopes, classifications) by tenant_id — not as a feature, as a property enforced at the type level. §6.3 Tokenisation invariants

Force 4 — Industry extensibility

Seven verticals (RC, HLS, ER, AXLE, TMT, TH, ICE) with overlapping standards (FHIR + CIM for healthcare + energy; J1939 + ISA-95 for manufacturing + equipment). The design's four incorporation patterns (A identifier, B mirror, C consume-and-extend, D translator) let Practices reuse standards packages without forking. Without the pattern taxonomy, we'd vendor 30 standards eight times. §5 Industry standards stance

Design tension — velocity vs auditability

The design explicitly ranks auditability over autonomy (§2 principle 1). This has cost us at least three “simpler” sprint outcomes. Example: Sprint 12's emitter could have skipped content-addressed I/O — store inputs inline, one less moving part, −80 LOC. We chose the harder path because a 10 MB Gold query inlined on every row blows up the ledger at scale, and dedup across rows requires the hash. Velocity lost: ~4 hours. Future cost avoided: O(N·K) bytes where K grows with agent adoption. This is the kind of choice the design doc makes for us; the implementation ratifies it.

2. Core & Schemas (Sprints 1–2)

Narrative
Narrative hidden. Press Start in the bar above to expand and hear the summary, or Show to expand without narration.

This is the foundation — sprints one and two. Think of it as the dictionary every other package has to speak. apex-core ships seven manifest kinds as Pydantic v2 models, all frozen, all strict. Schema, event, agent, orchestration, policy, tenant, and service — each with its own validator.

We built a SemVer classifier that's quietly doing most of the heavy lifting. Give it an old version and a new version; it returns patch, minor, or major. Sprint eleven's gate resolver calls that same function to decide whether a step is zero-touch or needs a human. Same logic, one implementation, no drift.

apex-schemas-common adds the shared entity base — canonical entity, SCD type two fields, envelope binding — plus a Delta DDL generator that writes Spark tables straight from a Pydantic class. The clever bit is classification propagation. We use Python's Annotated type to tag sensitive fields — Annotated PHI, Annotated PII, Annotated PCI — and a walker pulls those labels out at runtime. Purview, the tokenizer, and the visibility lattice all read the same metadata. No sidecar YAML that drifts. No duplicate truth.

The standards registry is keyed by ID, not by authority name, which bit us early in sprint two when ICD-10-CM didn't match the string CDC NCHS. Twenty-four standards in there today: GTIN, SSCC, GLN, LOINC, ICD-10, NDC, CPT, HCPCS, RxNorm, SNOMED-CT, EIDR, the full list. When an auditor asks which standard governs a field — one lookup, one answer.

The foundation layer. Everything else in APEX negotiates against these types. apex-core defines the seven manifest kinds plus the canonical envelope plus SemVer + classify_bump; apex-schemas-common adds the reusable entity base, Delta DDL generator, Purview classification walker, and the 24-entry standards registry that every Practice package cites.

What & why

What: CanonicalEntity is the shared Pydantic base every Practice entity extends; it carries entity_id, SCD-Type-2 fields, and the envelope link. generate_delta_ddl() emits CREATE OR REPLACE TABLE … USING DELTA from a model class; walk_annotated_metadata() enumerates Annotated[T, Classification.X] tuples so Purview labels propagate from Python → Bronze/Silver/Gold automatically. The standards registry is keyed by standard_id (not by fuzzy authority string — that bit us in Sprint 2 when ICD-10-CM vs “CDC/NCHS” mismatched) and lists the four incorporation patterns: A identifier, B mirror, C consume+extend, D translator.

Why: Design (§5 industry-standards stance, §14 Purview) positions APEX as not a standards reinventor — we consume GS1, HL7, IEC 61970, ISA-95, and thirty others. The registry makes that stance machine-checkable: every Practice-entity field that holds a standardised identifier declares StandardRef(standard_id=…), and the registry maps that ID to its authority, URL, version, and incorporation pattern. When an auditor asks “what standard governs this field?” the answer is one lookup, not a tribal recollection.

Implementation strategy — why Pattern C (Annotated) for classifications

We considered three classification-propagation designs: (1) a separate sidecar YAML mapping field paths to labels, (2) subclassing FieldInfo, (3) Annotated[T, Classification.PHI] as Pydantic v2 metadata. We picked Pattern C because it travels with the model across import boundaries, serialises trivially in Purview extraction, and costs zero runtime overhead — model_fields exposes the metadata tuple directly. The Purview walker is ~40 lines. Sidecar YAML would have drifted the moment someone forgot to update it; subclassing FieldInfo would have coupled us to Pydantic internals we cannot pin.

Why frozen strict Pydantic, not dataclass

Design §2 demands value-equal manifests for deterministic hashing. Two YAMLs that serialise to the same manifest must produce the same manifest_version SHA. dataclass(frozen=True) gives equality but no strict parsing — a typo silently coerces. Pydantic v2 with ConfigDict(strict=True, frozen=True) gives both: strict input parsing (no silent string-to-int coercion) and hashable equality. The manifest hash becomes a true content identifier, not a representation hash. This is load-bearing for the three-version rule.

3. Practice Mesh (Sprint 3)

Narrative
Narrative hidden. Press Start in the bar above to expand and hear the summary, or Show to expand without narration.

Ten practice packages, one per vertical. SCML for supply chain. MERML for merchandising. CXML for customer. HLSCML for clinical. ERCML for energy. AXLECML for manufacturing. TELML, THML, and ICEML for telecom, travel, and industrial equipment. Each ships a small set of Pydantic entities — typically six to eleven — citing standards by ID, not by re-implementing them.

The real decision here was when to vendor a standard as its own package versus inlining it. The rule we settled on: extract if two or more practices use it, or if it's over two hundred lines of content. FHIR goes into its own package because HLS uses it and a future claims practice will too. ISA-95 gets its own package because manufacturing and energy both consume it. GTIN-14 stays inline — it's a single identifier. Eight standards packages in total: FHIR, ISA-95, CIM, SID, J1939, ISO-14224, OpenTravel, and CDISC.

Round-trip translators are where the work is. HLSCML has four: FHIR round-trips cleanly — the test suite asserts an exact round-trip through Patient, Observation, Encounter. HL7 v2 and CDA are stubs for now with the ADT and CCD skeletons in place. AXLECML translates both ISA-95 equipment hierarchies and J1939 signal frames. Every translator is a pure function, tested with a round-trip assertion. We consume industry standards. We don't reinvent them.

Ten Practice-specific schema packages covering the supply chain, merchandising, customer, healthcare, energy, manufacturing, telecom, travel, and industrial-equipment verticals — each built on CanonicalEntity, citing standards via StandardRef, and shipped with round-trip translators to/from the native industry format. Eight separate Pattern-B standards packages hold the standards themselves so Practices sharing a standard (FHIR, ISA-95, CIM, SID) reuse one package instead of forking.

What & why — why a custom tokenizer instead of a standard library

What: TokenService derives a deterministic 16-character base64url token via HMAC-SHA256(key=K, msg=tenant_id|classification|plaintext). The vault stores token → plaintext scoped by (tenant, classification) composite key. Detokenisation is a vault lookup, not algorithm reversal — you can rotate keys without losing past mappings.

Why: Design (§6.3 tokenisation invariants, §8 medallion) requires three properties no off-the-shelf library gave us: (1) classification-separation so the same email under “Confidential” and under “Restricted” mints two different tokens (downstream sinks with different label entitlements must see different surrogates); (2) tenant-separation so Tenant A's token for foo@bar.com never collides with Tenant B's; (3) deterministic output so Silver joins work on tokens without a round-trip through the vault. A standard reversible format-preserving-encryption library solves none of these cleanly.

Implementation strategy — notebooks vs Python packages

The medallion pipeline runs inside Fabric notebooks that talk PySpark. We split the code in two: plain Python modules (apex-medallion) hold the pure logic — transforms, schema drift, measure specs, SCD2 upsert plans — with no pyspark import at module level. Notebook templates (notebooks/bronze/, notebooks/silver/, notebooks/gold/) import the Python modules and inject the Spark session. Ruff + mypy + pytest exclude the notebooks/ tree; the Python tree uses TYPE_CHECKING guards so SparkSession annotations type-check without a PySpark install. Result: CI runs in 1.3 seconds against 41 packages and zero notebooks; Fabric runs the same code at cluster scale.

What & why — pausable Orchestrator

What: Orchestrator.run(inputs) executes steps until a HITL gate fires, at which point it returns OrchestrationResult(status=PAUSED, pending_approvals=[pending_id]). The caller persists pending_id, shows a Teams card, waits for human decision, then calls Orchestrator.resume(pending_id, decision, approver_id, rationale). Run state lives in the ApprovalsClient, not in process memory.

Why: Design (§9 HITL runtime; §10 orchestration) says HITL waits may be minutes (Teams card) to hours (off-hours approval). A synchronous await would pin a compute worker for the duration. By externalising the pause state we can shed the worker immediately after pause and rehydrate on resume — making HITL free at steady-state. What & why — raw CoT goes to a restricted store

What: The emitter accepts raw_reasoning: str, but never writes it to the main ledger or the content-addressed store. Instead it goes to RestrictedTraceStore keyed by decision_id, with a distinct access scope. Only the DLP-scrubbed StructuredReasoning (tool-call sequence, justification summary, cited-evidence pointers, confidence) gets content-hashed into the main row.

Why: Design (§11.4) warns that raw chain-of-thought contains PHI, PCI, trade secrets, and hallucinations. Auditors rarely need it; incident investigators sometimes do. Routing it to a stricter-access store gives us both legal defensibility (we kept the evidence) and privacy minimisation (99% of readers never see it). The store is typed as its own class so the linter and reviewers can't accidentally plumb raw traces into the main ledger path.

Implementation strategy — content-addressed I/O decouples row from payload

Storing actual input dicts and tool-result dicts inline in the audit row would make rows enormous (a single Gold query can return 10 MB) and would prevent dedup (the same input hits many rows). Instead ContentAddressedStore.put(payload) returns sha256:<hex>; the row stores the ref. Same payload → same ref → one copy. Auditors resolve via AuditEmitter.resolve_decision(did) which dereferences both the inputs and the reasoning trace. Production wires the in-memory store to a Delta-backed blob store with WORM + retention; the contract is unchanged.

Component strategy — what must hold as we add Sprints 13-19

1. Contracts freeze before runtimes ship

Sprints 13–19 all touch the runtime. None of them may modify a Pydantic model shipped in Sprints 1–12 without a MAJOR bump of its package. The fleet validator (from Sprint 1) + classify_bump (from Sprint 1) already enforce this in CI. If a Sprint 13 commit tries to add a required field to AuditRow, CI fails the PR.

2. MCP is the only cross-plane boundary

No Foundry agent imports apex-medallion. No notebook imports apex-orchestrator. Cross-plane calls go through MCP tools, which means they get traced, scope-checked, and audit-rowed automatically. This is the invariant that makes Sprint 13 Purview lineage work without code changes in 40 packages.

3. Every new Practice reuses the same five foundations

apex-core, apex-schemas-common, apex-tokenizer, apex-identity, apex-audit. A new vertical (say, a Public-Sector Practice) ships one entity package + zero platform packages. If we find ourselves adding a new platform package per Practice, the design failed.

4. Auditability beats feature velocity

Every PR that lands in Sprints 13–19 must produce audit rows for its happy path. The fleet validator includes a pragmatic check: a new orchestration manifest that does not cite the apex-audit emitter fails CI. This keeps the 14-field contract load-bearing.

5. Deterministic wherever it costs nothing

Content hashes, HMAC tokens, SemVer bump resolution — all pure functions. Flaky tests in this codebase would indicate we introduced non-determinism; CI treats any test-flake as a P1 bug.

6. Tenant isolation is a property, not a feature

Tokens, audit rows, scopes, policies, classifications — every one of these is composite-keyed by tenant_id. A tenant-A agent cannot detokenise a tenant-B token, cannot read a tenant-B row, cannot inherit a tenant-B scope. Sprints 13–19 must preserve this. Any shared-dict pattern in a new package is a review red flag.

def validate_classifications(entity_cls: type[BaseModel]) -> ClassificationResult: ...

Heuristic for unclassified_sensitive: any field whose name matches /(_token$|email|phone|ssn|mrn|dob|address|account_num|card)/i and lacks a Classification annotation is flagged. Reported as warning, not failure — false positives are real (e.g. a legitimate contact_description).

Tokenisation (dynamic check per parsed entity)
@dataclass(frozen=True)
class TokenisationResult:
    entity_cls_name: str
    row_id: str
    ok: bool
    tokenised_fields: tuple[str, ...]
    failures: tuple[str, ...]   # determinism / separation / round-trip failures

def validate_tokenisation(
    entity: BaseModel,
    token_service: TokenService,
    tenant_id: str,
) -> TokenisationResult: ...

Exercises the four design invariants (§6.3): determinism (same plaintext → same token), classification separation (different labels → different tokens), tenant separation (different tenants → different tokens), vault round-trip (detokenise returns plaintext). Fresh InMemoryVaultBackend per test.

2.6 — HarnessReport (report.py)

Aggregates the three validator result streams. coverage_matrix() is what a developer looks at on failure — shows per-entity which fields got exercised by at least one fixture and which were never hit. Coverage gaps are warnings, not failures.

@dataclass(frozen=True)
class HarnessReport:
    practice: str                                      # "rc"
    tenant_id: str
    shape_results: tuple[ShapeResult, ...]
    classification_results: tuple[ClassificationResult, ...]
    tokenisation_results: tuple[TokenisationResult, ...]

    @property
    def passed(self) -> bool: ...
    def coverage_matrix(self) -> dict[str, dict[str, str]]: ...   # entity -> field -> status
    def summary(self) -> str: ...                                 # one-line per-entity
Embedded design decisions resolved in Section 2

Warnings, not failures, for unclassified_sensitive. The regex heuristic will false-positive on fields like contact_description; CI shouldn't block on those.

Fresh InMemoryVaultBackend per test. Determinism + isolation. Production tokenizer service wired to a real Delta-backed vault is not what the harness tests.

Polyfactory over hypothesis.strategies.from_type. Pydantic-native, more predictable for v2 models. Hypothesis is more powerful but adds ceremony we don't need at MVP.

    entity_cls, yaml_file = _ENTITIES[entity_name]

from apex_rc.cxml.entities import Customer
from apex_test_harness import run_scenario

def test_scenario(scenario, bronze_schema, rc_sim, rc_validator):
    row = build_bronze_row_from_scenario(scenario, Customer)
    rc_sim.seed_rows(bronze_schema.conn, bronze_schema.schema, [row])

        validator=rc_validator, tenant_id="t-harness",

def test_rc_practice_bundle_parses_end_to_end(
    bronze_schema, rc_sim, rc_validator
