## 1. Why this document

The framework-wide [`Roadmap.md`](Roadmap.md) tracks the L1 contract, schemas, MCP servers, identity, and the platform layer — most of which is complete (see Sprints 1–29 in that file). What it does **not** track at the RC level is:

- Which of the **7 RC services** are scaffolded vs. implemented vs. deployed.
- Which **scenarios** (featured + catalog) are in scope per sprint.
- Which **agents** in each scenario have prompts + MCP tools wired.
- The **deployment sequence** — which service goes first, which fuses into which.

This plan fills that gap and ties to the wizard so progress is visible to whoever is configuring the next deployment.

## 5. How to update progress

1. **For a single item check-off:** edit [`services/rc/_build-status.yaml`](../../services/rc/_build-status.yaml), set `done: true` on the item.
2. **For a service status change:** edit the same file, set `services.{CODE}.status` (`planned` → `scaffolded` → `implemented` → `deployed` → `pilot` → `ga`).
3. **For a new featured scenario:** mark `Featured?` = `⭐ Featured` in [`APEX-Scenario-Chains.xlsx`](../reference/APEX-Scenario-Chains.xlsx), re-run [`tools/gen_services_tree.py`](../../tools/gen_services_tree.py), then add it to `_build-status.yaml`.
4. **For a new agent role at service level:** add to [`services/_extras.yaml`](../../services/_extras.yaml) under that service code, re-run the generator, then add the agent under each scenario in `_build-status.yaml`.
5. The wizard's `/roadmap` page reflects YAML changes on next page load. The treeview reflects status badges on next API call.
