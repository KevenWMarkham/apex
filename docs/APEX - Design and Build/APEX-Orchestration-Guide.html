This guide names the primitives, maps them to Azure, mocks the dashboard you actually want, and proposes the APEX pattern that makes it reusable across editions.

§1 · The frame

The four concerns you must not conflate

Most teams pick a framework, try to do all four at once, and find that the framework's opinions about one concern break how they need to solve another. Separate them. Decide each explicitly. Then pick the framework that supports your decisions — not the other way around.

01 · Spawning

How the parent creates and configures children

Naming, identity scope, tool access, budget envelope, initial state. Every child is born with a declared shape; it does not discover its own permissions at runtime.

02 · Monitoring

How the parent observes progress without blocking

Children emit events; parents subscribe. Pull-polling is an anti-pattern — it couples parent availability to child liveness. Push via append-only log, always.

03 · Control

How the parent intervenes — pause, redirect, kill

Control is about revoking permission to continue, not terminating processes. Cooperative cancellation beats signal-level termination every time in production.

04 · Reconciliation

How child outputs merge back without stomping

Declare the merge policy at DAG design time, not at runtime. Last-write-wins is the source of most silent corruption incidents in agent systems.

The four patterns — pick one explicitly

For APEX engagements — Nike R2R, Samsonite, the RC edition playbook — supervisor-worker with a DAG spine is the right default. It matches Azure AI Agent Service's native shape, it's what SteerCo reviewers can reason about, and it gives you clean kill semantics.

PatternParent → child relationshipBest forKill semantics
DAG directed acyclicParent defines graph; children run per topologyDeterministic workflows with known steps (close, reconciliation)Cancel downstream; upstream unaffected

The key move

If you can't draw the parent-child relationship on a whiteboard in under 90 seconds, the pattern is wrong. Supervisor-worker with a DAG spine fits this bar; swarm never does.

§2 · Control primitives & kill levels

Don't kill the process. Revoke permission to continue.

The single most important design decision in production multi-agent systems. You externalize three primitives — every child agent checks them between steps — and killing becomes cooperative, predictable, and auditable.

01

Cancellation token

Not a signal. A flag in shared state that children poll between steps. At minimum, between any two tool calls.

Cancellation is cooperative. No orphaned tool calls. No half-written database rows. No dangling HITL prompts.

while not cancel_token.is_set():
    step()
02

Budget envelope

Declared at spawn time. Max wall-clock, max tool calls, max tokens, max cost, max recursion depth.

The child enforces it on itself and exits gracefully on breach. Your protection against runaway recursion and cost surprises.

budget = {
  wall_s: 480,
  tool_calls: 40,
  cost_usd: 2.0,
  depth: 2
}
03

Status channel

Append-only log keyed by run_id + child_id. Children emit progress events: step_started, tool_called, awaiting_hitl, heartbeat, cancelled, error.

Parents read this stream. Parents never poll children. This inverts control direction and makes monitoring cheap.

How the three primitives compose into a kill

Set the cancel token → wait for the child's next heartbeat → confirm a cancelled event in the log. If no heartbeat arrives within N seconds, declare the child stuck and mark for cleanup. No shutting-down-the-VM, no kill -9, no orphaned writes.

The four kill levels — offer the spectrum, let the human pick

Not all kills are equal. A SteerCo partner who wants to "kill it" almost always means pause or soft cancel. Abort is the wrong default and will destroy trust the first time it corrupts state.

LevelWhat it doesWhen to useState preservation
Pause reversibleSets a pause flag; children stop between steps, hold state in placeInvestigate, then maybe resumeFull — resumable
Soft cancel defaultSets cancel token; children finish current step, write state, exitHuman-triggered stop — preserves partial workPartial — committed steps survive
Hard cancel emergencySoft cancel + abandons in-flight tool calls if idempotentBudget breach, policy violation detected mid-runUncertain — in-flight step may or may not commit
Abort last resortTerminates child processes immediately; may leave orphaned writesContained damage only. Requires cleanup job.None — may corrupt state
Anti-pattern to name and kill

Any framework that offers only one kill primitive — usually labelled terminate() or stop() — is missing the spectrum. You will use it, it will corrupt state, and your team will stop trusting the orchestrator. Demand the four levels before you commit to a framework.

§3 · The Microsoft mapping

Durable Functions is the parent. Agent Service is the child.

The orchestrator doesn't run the children — it dispatches them, then awaits events on the Event Hub stream. This gives you free replay-ability of the orchestration for debugging, durable state across restarts, and an already-governed path for Entra identity and Purview classification.

The architectural move

The orchestrator doesn't execute the agents — it dispatches them. Children run as independent Agent Service instances. The parent sits on an Event Hubs subscription and reacts to events. This is the pattern Azure is actually designed for; it gives you durable replay for debugging, and it means the parent can restart without the children noticing.

§4 · The five-lane dashboard

If the dashboard can't answer "why is this slow?"
in thirty seconds, it's wrong.

Most teams build dashboards that show "which agents are running" and call it done. That tells you nothing useful when something breaks. What you actually want is a per-run timeline view with five lanes — topology, budget, HITL, tool calls, interventions — rendering the same event stream the parent orchestrator subscribes to.

§5 · Five failure modes

These will bite you. Plan for them on day one.

Not optional. Every one of the five shows up in production within the first fifty runs. Each has a diagnostic signature (how you recognize it), a trigger (what set it off), and a mitigation (the primitive that prevents it). Build the mitigation before you need it.

F1

Zombie children

Signature: parent thinks the child is dead; child is still running, still calling tools, still writing to state.

Trigger: parent-side timeout without confirming child-side cancel event.

Mitigation: heartbeat timeout on the parent triggers parent-side reconciliation, not child-side watchdog. Parent revokes the child's Entra scope to hard-stop writes.

F2

Split-brain HITL

Signature: two parallel children get contradictory approvals from two different humans.

Trigger: HITL prompts flow through per-child queues instead of a single parent queue.

Mitigation: every HITL approval request routes through a single parent-level queue with correlation IDs. Siblings that reach for the same approval serialize.

F3

Cost runaway from recursion

Signature: child spawns grandchild spawns great-grandchild. Cost balloons. Nothing looks wrong until the bill arrives.

Trigger: no depth limit in the spawn primitive. Children think recursion is free because the parent didn't say otherwise.

Mitigation: depth limit declared in the budget envelope at spawn time. Enforced on the parent side before allowing a child to request its own spawn.

F4

Stuck HITL

Signature: human never responds to an approval prompt. Run hangs forever. Budget for active agents quietly burns.

Trigger: HITL prompt with no deadline, no escalation, no fallback path.

Mitigation: every HITL has a deadline. Expiry triggers a declared policy — auto-cancel, escalate to a named second approver, or take a defined fallback action. Never indefinite wait.

F5 · The quietest and nastiest

Partial success ambiguity

Signature: eight of ten children succeeded. The orchestrator doesn't know what "done" means. It proceeds anyway. Downstream steps use incomplete state.

Trigger: no explicit success/partial/failure policy declared at DAG design time. Someone wrote "wait for all" and meant "wait for most." The framework picked the literal interpretation.

Mitigation: every DAG node declares its completion policy explicitly — all-must-succeed, quorum(n), best-effort, required-set. Framework fails the run at design-time validation if the policy is missing. No runtime defaults.

Honest note on frameworks

None of the orchestration frameworks in the market today handle all five failure modes well — not LangGraph, not Semantic Kernel, not CrewAI, not AutoGen, not OpenAI's Agents SDK. Each nails two or three, punts on the others. The glue is real engineering work, and it's exactly the accumulated pattern work APEX should make reusable so Deloitte doesn't rediscover it three times.

§6 · Recommended APEX additions

Make it an inheritable pattern, not a bespoke build.

Two additions to APEX that take the orchestration lessons out of any single engagement and put them in the kernel where every edition inherits them. Both natural extensions of work already done — the ORCH namespace is already established, and the MCP tool catalog naming convention is already defined.

Addition 1 · apex.orch.control pattern spec

A sibling to the RC ORCHs. Defines the control plane as a reusable contract across editions. Every concrete ORCH inherits this — so spawn, monitor, and kill behavior is identical across Retail, Healthcare, Energy.

Addition 2 · rc.orch.* MCP tool family

Orchestration telemetry exposed through the same MCP abstraction used for everything else. Humans and higher-level agents drive the control plane through governed tool calls. Every cancel becomes a Purview-audited event, not a side-channel operation.

Why the rc.orch family matters

The governance story stays clean. A SteerCo partner who cancels a run does it through a Purview-audited tool call attributed to their Entra identity — same audit plane as every other agent action. No separate "admin console" with its own access model, its own audit gap, and its own way to go wrong.
