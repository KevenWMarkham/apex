1.1 The Engagement at a Glance

Vuori is a $2B premium activewear brand competing with Lululemon, Alo Yoga, On Running, and Nike. 1.6 The Build-Environment Constraint

Hard requirement

All builds run inside Vuori's environment — Snowflake on Azure + Azure AI Foundry. This is a CIO requirement reaffirmed in the Dallas offsite, not a preference. APEX agents read from Vuori's CURATED Snowflake layer, write to Vuori's Purview audit ledger, and never leave the tenant. The synthetic data shown in this book is for laptop and dev substrates only; stage and prod target the client tenant.

This constraint shapes every architecture decision in Parts II and III: Snowflake (not Cosmos) for state; Azure Data Factory + Fivetran (not custom) for ingestion; Azure AI Foundry (not a third-party hosted LLM) for model serving; LEDGER on Purview (not on a Deloitte-side store).

2.4 The Persona-Principal Binding

Per Sprint 47.6, every persona must bind to one of four modes before PSG-15 will allow a stage/prod deploy:

The Vuori YAML above mixes all four: The Finance Lead is bound to the CFO directly, The Briefer to a hybrid roster, and the analyst/checker/ops to groups.

PSG-15 fails closed

If any REPLACE_WITH_* placeholder survives in a stage/prod use-case YAML, PSG-15 (Persona-Binding Resolvability) returns RED and the wizard's deploy button refuses to fire. This is intentional. The operator must paste the real Entra Object IDs at deploy time. Until then, run on laptop substrate where synthetic personas are allowed.

3.1 The ADR-006 Pattern Library

The Microsoft Agent Framework defines five canonical orchestration patterns. APEX's agent_framework_loader (Sprint 42) enforces that every agent declares which pattern it implements. For the Vuori WBR:

PatternWhere it's used in the WBR journey
SequentialWithin each persona's /run — the 5 steps of UC-01 (pull → compute → rank → diagnose → route) execute in order.
HandoffBetween personas — Analyst routes to Demand Checker (UC-01 → UC-02), Demand Checker routes to Finance Lead (UC-02 → UC-04).
ConcurrentInside The Finance Lead — OTB / margin / markdown / spend guardrails (UC-04..UC-07) check in parallel; first failure short-circuits.
Group ChatBrief Synthesis — UC-11/12/13 contribute Done / Your-Call / Watch bucket items to a shared brief object.
MagenticGate-6 calibration (weekly) — recursive planning loop tunes thresholds based on prior week's outcomes. Out of Q1 scope; design-frozen for Q2.

3.2 The Shared FastAPI Base

Every persona ships as a containerised FastAPI service with two routes: /healthz for Docker health checks and /run for invocation. The shared base is 30 lines:

# MVP/agentic-merch/src/agentic_merch/base.py
"""Shared FastAPI service template for any agent persona."""
from __future__ import annotations
from typing import Any, Protocol
from fastapi import FastAPI


class AgentRunner(Protocol):
    """Per-persona business logic. Returns (result_dict, ledger_rows)."""
    def run(self, **kwargs: Any) -> tuple[dict[str, Any], list[dict[str, Any]]]:
        ...


def build_agent_app(*, runner: AgentRunner, agent_id: str) -> FastAPI:
    """Build a FastAPI app exposing POST /run and GET /healthz for one persona."""
    app = FastAPI(title=f"agent-{agent_id}", version="0.1.0")

    @app.get("/healthz")
    def healthz() -> dict[str, str]:
        return {"status": "ok", "agent_id": agent_id}

    @app.post("/run")
    def run(body: dict[str, Any]) -> dict[str, Any]:
        result, ledger_rows = runner.run(**body)
        if ledger_rows:
            result["_ledger_rows"] = ledger_rows
        return result

    return app

The contract is deliberately thin: a runner returns (result, ledger_rows). Everything else — auth, MCP tool wiring, agent framework patterns — layers on top in the persona modules.

from __future__ import annotations
from dataclasses import dataclass
from enum import Enum
from pathlib import Path
import yaml


class Pattern(str, Enum):
    SEQUENTIAL = "sequential"
    CONCURRENT = "concurrent"
    HANDOFF = "handoff"
    GROUP_CHAT = "group_chat"
    MAGENTIC = "magentic"


@dataclass
class AgentSpec:
    id: str
    pattern: Pattern
    mcp_dependencies: list[str]
    hitl_gate: str
    yaml_path: Path

    @classmethod
    def load(cls, yaml_path: Path) -> "AgentSpec":
        data = yaml.safe_load(yaml_path.read_text())
        return cls(
            id=data["id"],
            pattern=Pattern(data["agent_framework_pattern"]),
            mcp_dependencies=data.get("mcp_dependencies", []),
            hitl_gate=data["hitl"]["gate"],
            yaml_path=yaml_path,
        )

3.7 The Handoff Wiring

Handoff between personas is implemented as an HTTP call from the upstream persona to the downstream one, mediated by the routing_engine:

# MVP/TestHarness/src/mvp_test_harness/stubs/routing_engine.py — stub
"""Routing engine — fan-out handoff from The Analyst to downstream personas."""
from __future__ import annotations
from typing import Any
import httpx


PERSONA_URLS = {
    "agent_1":  "http://the-demand-checker:8000/run",
    "agent_4":  "http://the-finance-lead:8000/run",
    "agent_8":  "http://the-operations-lead:8000/run",
    "agent_13.3": "http://the-briefer:8000/run",
}


def route(routed_to: list[str], payload: dict[str, Any]) -> dict[str, Any]:
    """Fan out to each downstream persona. Returns per-target responses."""
    results = {}
    for agent_id in routed_to:
        url = PERSONA_URLS[agent_id]
        with httpx.Client(timeout=30.0) as c:
            results[agent_id] = c.post(url, json=payload).json()
    return results

Concurrent handoff is fan-out at the routing layer. Sequential handoff (Demand Checker → Finance Lead) is one URL only. Both shapes use the same primitive.

Note · Why HTTP, not in-process

Each persona runs as its own container with its own identity (Entra Agent ID), its own MCP credentials, and its own scaling profile. The Operations Lead might need 2 vCPU during a big rebalance while The Briefer sits idle. HTTP between personas is the substrate boundary that lets each scale independently — and gives the LEDGER a natural per-call audit point.

# services/rc/rc-wbr/tools/generate_vuori_synthetic.py
"""Generate Vuori-shaped synthetic data for the laptop substrate.

Models actual constraints: dual calendar, MAC-only margin, limited season codes,
launch_date as markdown-aging proxy.
"""
from __future__ import annotations
import datetime as dt
import random
from pathlib import Path
import pandas as pd

OUT = Path("synthetic")
OUT.mkdir(exist_ok=True)
random.seed(42)

DIVISIONS  = ["Mens", "Womens", "Accessories"]
CATEGORIES = {
    "Mens":        ["Pants", "Shorts", "Outerwear", "Tops", "Joggers"],
    "Womens":      ["Pants", "Leggings", "Tops", "Outerwear", "Lounge"],
    "Accessories": ["Hats", "Bags", "Socks"],
}
COLLECTIONS = ["Dream Knit", "Restore", "Performance", "Core Cotton"]
REGIONS     = ["Pacific", "Mountain", "Midwest", "Southeast", "Northeast"]


def gen_products(n_styles: int = 200) -> pd.DataFrame:
    rows = []
    for i in range(n_styles):
        div = random.choice(DIVISIONS)
        cat = random.choice(CATEGORIES[div])
        style_id = f"V{i+1000:04d}"
        for color in random.sample(["Black", "Navy", "Gray", "Olive", "Stone", "Rust"], k=3):
            rows.append({
                "sku":            f"{style_id}-{color[:3].upper()}",
                "style_id":       style_id,
                "color":          color,
                "division":       div,
                "category":       cat,
                "class_name":     f"{cat} v{(i % 5) + 1}",
                "collection":     random.choice(COLLECTIONS),
                "launch_date":    dt.date(2025, 9, 1) + dt.timedelta(days=random.randint(0, 240)),
                "intended_exit":  dt.date(2026, 8, 31),
                "mac_cost":       round(random.uniform(8.0, 32.0), 2),
                "list_price":     round(random.uniform(48.0, 168.0), 2),
            })
    return pd.DataFrame(rows)


def gen_calendar(start: dt.date, end: dt.date) -> pd.DataFrame:
    rows, d = [], start
    while d <= end:
        rows.append({
            "date":              d,
            "gregorian_month":   d.month,
            "gregorian_quarter": (d.month - 1) // 3 + 1,
            "nrf_week":          ((d - dt.date(2025, 2, 2)).days // 7) + 1,
            "nrf_month":         _nrf_month(d),
        })
        d += dt.timedelta(days=1)
    return pd.DataFrame(rows)


def _nrf_month(d: dt.date) -> int:
    """NRF 4-4-5 mapping. February starts the retail year."""
    week = ((d - dt.date(2025, 2, 2)).days // 7) + 1
    pattern = [4, 4, 5, 4, 4, 5, 4, 4, 5, 4, 4, 5]
    month, cum = 1, 0
    for w in pattern:
        cum += w
        if week <= cum:
            return month
        month += 1
    return 12


def gen_sales(products: pd.DataFrame, calendar: pd.DataFrame,
              n_weeks: int = 52) -> pd.DataFrame:
    """52 weeks of weekly sales per (sku × region). Bakes the Wk16 Midwest miss."""
    weeks = calendar.groupby("nrf_week").first().reset_index().head(n_weeks)
    rows = []
    for _, p in products.iterrows():
        for region in REGIONS:
            for _, w in weeks.iterrows():
                base_units = random.gauss(40, 10)
                # Bake the demo scenario: Apparel · Midwest · Wk16 · −12%
                if region == "Midwest" and w.nrf_week == 16 and p.category in {"Pants", "Tops"}:
                    base_units *= 0.88
                units = max(0, int(base_units))
                revenue = round(units * p.list_price * random.uniform(0.7, 1.0), 2)
                cost = round(units * p.mac_cost, 2)
                rows.append({
                    "sku": p.sku, "region": region, "nrf_week": int(w.nrf_week),
                    "units": units, "revenue": revenue,
                    "mac_cost": cost, "mac_margin": round(revenue - cost, 2),
                    "markdown_flag": revenue < units * p.list_price * 0.85,
                })
    return pd.DataFrame(rows)


if __name__ == "__main__":
    products = gen_products()
    calendar = gen_calendar(dt.date(2025, 2, 2), dt.date(2026, 1, 31))
    sales = gen_sales(products, calendar)
    products.to_parquet(OUT / "dim_product.parquet", index=False)
    calendar.to_parquet(OUT / "dim_calendar.parquet", index=False)
    sales.to_parquet(OUT / "fact_sales.parquet", index=False)
    print(f"wrote {len(products)} skus, {len(calendar)} days, {len(sales)} sales rows")

  EXTRACT(MONTH   FROM calendar_date)                            AS gregorian_month,
  EXTRACT(QUARTER FROM calendar_date)                            AS gregorian_quarter,
  -- NRF 4-4-5: retail year starts the Sunday on or after Feb 1
  FLOOR(DATEDIFF('day', '2025-02-02'::date, calendar_date) / 7) + 1
    AS nrf_week_of_year,
  CASE
    WHEN FLOOR(DATEDIFF('day', '2025-02-02'::date, calendar_date) / 7) + 1
         BETWEEN 1  AND 13 THEN 'Q1'
    WHEN FLOOR(DATEDIFF('day', '2025-02-02'::date, calendar_date) / 7) + 1

         BETWEEN 27 AND 39 THEN 'Q3'
    ELSE 'Q4'
  END                                                            AS nrf_quarter,
  DAYOFWEEK(calendar_date)                                       AS day_of_week,
  CASE WHEN DAYOFWEEK(calendar_date) IN (0, 6) THEN TRUE ELSE FALSE END
                                                                 AS is_weekend
FROM days
WHERE calendar_date BETWEEN '2025-02-02' AND '2028-01-31'

6.3 The Three Tools UC-01 Needs

# services/rc/rc-wbr/mcp/merml-mcp/src/merml_mcp/tools.py
"""merml-mcp tools — Vuori CURATED reads for The Analyst, Finance Lead, Ops Lead, Briefer."""
from __future__ import annotations
from dataclasses import dataclass
from typing import Any

from merml_mcp.snowflake import query
from merml_mcp.server import tool


@dataclass
class WeeklyActualsVsPlan:
    category: str
    region: str
    nrf_week: int
    actual_units: int
    actual_revenue: float
    plan_units: int
    plan_revenue: float
    miss_pct_units: float
    miss_pct_revenue: float


@tool(
    name="fetch_weekly_actuals_vs_plan",
    description="Pull weekly actuals vs. plan for every category × region in a given NRF week.",
)
def fetch_weekly_actuals_vs_plan(nrf_week: int) -> list[WeeklyActualsVsPlan]:
    """Returns one row per (category, region) for the given week."""
    sql = """
      SELECT
        p.category, s.region, s.nrf_week_of_year AS nrf_week,
        SUM(s.units)   AS actual_units,
        SUM(s.revenue) AS actual_revenue,
        pl.planned_units    AS plan_units,
        pl.planned_revenue  AS plan_revenue,
        DIV0(SUM(s.units) - pl.planned_units, NULLIF(pl.planned_units, 0))
                            AS miss_pct_units,
        DIV0(SUM(s.revenue) - pl.planned_revenue, NULLIF(pl.planned_revenue, 0))
                            AS miss_pct_revenue
      FROM CURATED.curated__sales_with_aging s
      JOIN CURATED.dim_product p USING (sku)
      LEFT JOIN CURATED.fact_plan_bottomsup pl
        ON pl.category = p.category
       AND pl.region   = s.region
       AND pl.nrf_week = s.nrf_week_of_year
      WHERE s.nrf_week_of_year = %(nrf_week)s
      GROUP BY p.category, s.region, s.nrf_week_of_year, pl.planned_units, pl.planned_revenue
    """
    rows = query(sql, {"nrf_week": nrf_week})
    return [WeeklyActualsVsPlan(**r) for r in rows]


@tool(
    name="compute_consecutive_miss_count",
    description="For a (category, region), count consecutive prior weeks where actual < plan.",
)
def compute_consecutive_miss_count(category: str, region: str, through_week: int) -> int:
    sql = """
      WITH ordered AS (
        SELECT s.nrf_week_of_year AS wk,
               SUM(s.revenue) - pl.planned_revenue AS gap
        FROM   CURATED.curated__sales_with_aging s
        JOIN   CURATED.dim_product p USING (sku)
        LEFT   JOIN CURATED.fact_plan_bottomsup pl
            ON pl.category = p.category AND pl.region = s.region
           AND pl.nrf_week = s.nrf_week_of_year
        WHERE  p.category = %(category)s AND s.region = %(region)s
           AND s.nrf_week_of_year <= %(through_week)s
        GROUP BY 1, pl.planned_revenue
        ORDER BY 1 DESC
      ),
      ranked AS (
        SELECT wk, gap, ROW_NUMBER() OVER (ORDER BY wk DESC) AS rk FROM ordered
      )
      SELECT COUNT(*) AS consecutive_miss
      FROM   ranked
      WHERE  gap < 0
         AND rk = (SELECT MIN(rk) FROM ranked WHERE gap < 0) + (rk - 1)
    """
    return query(sql, {"category": category, "region": region,
                       "through_week": through_week})[0]["consecutive_miss"]


@tool(
    name="rank_exceptions_by_severity",
    description="Rank (category, region) exceptions by severity score for a given NRF week.",
)
def rank_exceptions_by_severity(nrf_week: int, top_n: int = 7) -> list[dict[str, Any]]:
    rows = fetch_weekly_actuals_vs_plan(nrf_week=nrf_week)
    scored = []
    for r in rows:
        consec = compute_consecutive_miss_count(r.category, r.region, nrf_week)
        # Severity = |miss_pct_revenue| × dollar_gap × consecutive_miss_count
        severity = abs(r.miss_pct_revenue) * (r.plan_revenue - r.actual_revenue) * max(consec, 1)
        scored.append({
            "category": r.category, "region": r.region,
            "miss_pct": r.miss_pct_revenue, "consecutive_miss_count": consec,
            "severity_score": severity,
        })
    scored.sort(key=lambda x: x["severity_score"], reverse=True)
    return [{**r, "severity_rank": i + 1} for i, r in enumerate(scored[:top_n])]

The Analyst's run() calls these three tools and emits the LEDGER row from §3.3. The SQL stays in the MCP. The agent stays declarative.

6.4 The Server Dispatch

# services/rc/rc-wbr/mcp/merml-mcp/src/merml_mcp/server.py
"""merml-mcp JSON-RPC dispatch over FastAPI."""
from __future__ import annotations
import inspect
from dataclasses import asdict, is_dataclass
from typing import Any, Callable

from fastapi import FastAPI, Header, HTTPException

from merml_mcp.auth import verify_agent_token

_TOOLS: dict[str, Callable[..., Any]] = {}
_TOOL_META: dict[str, dict[str, Any]] = {}


def tool(*, name: str, description: str) -> Callable:
    def decorator(fn: Callable[..., Any]) -> Callable[..., Any]:
        _TOOLS[name] = fn
        sig = inspect.signature(fn)
        _TOOL_META[name] = {
            "name": name, "description": description,
            "params": [{"name": p.name,
                        "type": p.annotation.__name__ if p.annotation != inspect.Parameter.empty else "any",
                        "default": None if p.default is inspect.Parameter.empty else p.default}
                       for p in sig.parameters.values()],
        }
        return fn
    return decorator


app = FastAPI(title="merml-mcp", version="0.1.0")


@app.get("/healthz")
def healthz() -> dict[str, str]:
    return {"status": "ok", "tools": str(len(_TOOLS))}


@app.get("/tools")
def list_tools() -> list[dict[str, Any]]:
    """MCP discovery — what tools does this server expose?"""
    return list(_TOOL_META.values())


@app.post("/call/{tool_name}")
def call(tool_name: str, args: dict[str, Any], authorization: str = Header(None)) -> Any:
    agent = verify_agent_token(authorization)        # raises 401 if Entra Agent ID invalid
    if tool_name not in _TOOLS:
        raise HTTPException(404, f"unknown tool: {tool_name}")
    fn = _TOOLS[tool_name]
    result = fn(**args)
    if isinstance(result, list):
        return [asdict(r) if is_dataclass(r) else r for r in result]
    return asdict(result) if is_dataclass(result) else result

Three routes: /healthz for Docker, /tools for MCP discovery (the agent introspects what's available), and /call/<tool_name> for invocation. Every call requires a valid Entra Agent ID bearer token — verified in auth.py.

6.6 The cxml-mcp Side

The Demand Checker (Agent 1) confirms whether the exception is a demand problem or a supply problem. Its two tools:

# services/rc/rc-wbr/mcp/cxml-mcp/src/cxml_mcp/tools.py
"""cxml-mcp tools — consumer signals for The Demand Checker and The Briefer."""
from __future__ import annotations
from dataclasses import dataclass

from cxml_mcp.snowflake import query
from cxml_mcp.server import tool


@dataclass
class IntentScore:
    category: str
    region: str
    nrf_week: int
    intent_score: float                # 0.0 .. 1.0
    historical_baseline: float
    diagnosis: str                     # "healthy" | "depressed"


@tool(
    name="compute_consumer_intent",
    description="Compute current intent score vs. historical baseline for a category × region × week.",
)
def compute_consumer_intent(category: str, region: str, nrf_week: int) -> IntentScore:
    sql = """
      WITH current_wk AS (
        SELECT AVG(wallet_share)      AS share_now,
               AVG(cross_shop_index)  AS xshop_now,
               AVG(search_volume)     AS search_now
        FROM   CURATED.fact_concon_signal
        WHERE  category = %(category)s AND region = %(region)s
           AND nrf_week = %(nrf_week)s
      ),
      baseline AS (
        SELECT AVG(wallet_share)      AS share_base,
               AVG(cross_shop_index)  AS xshop_base,
               AVG(search_volume)     AS search_base
        FROM   CURATED.fact_concon_signal
        WHERE  category = %(category)s AND region = %(region)s
           AND nrf_week BETWEEN %(nrf_week)s - 12 AND %(nrf_week)s - 1
      )
      SELECT
        -- Composite intent: 0.5 × normalized share + 0.3 × xshop + 0.2 × search
        LEAST(1.0, GREATEST(0.0,
          0.5 * (c.share_now  / NULLIF(b.share_base, 0)) +
          0.3 * (c.xshop_now  / NULLIF(b.xshop_base, 0)) +
          0.2 * (c.search_now / NULLIF(b.search_base, 0))
        )) AS intent_score,
        (b.share_base / NULLIF(b.share_base, 0)) AS historical_baseline    -- = 1.0 by definition
      FROM current_wk c, baseline b
    """
    row = query(sql, {"category": category, "region": region, "nrf_week": nrf_week})[0]
    score = row["intent_score"] or 0.0
    return IntentScore(
        category=category, region=region, nrf_week=nrf_week,
        intent_score=score,
        historical_baseline=row["historical_baseline"] or 1.0,
        diagnosis="healthy" if score >= 0.60 else "depressed",
    )


@tool(
    name="competitive_share_shift",
    description="Return competitor wallet share deltas vs. baseline for a category × region.",
)
def competitive_share_shift(category: str, region: str, nrf_week: int, top_n: int = 4) -> list[dict]:
    sql = """
      SELECT competitor,
             AVG(CASE WHEN nrf_week = %(nrf_week)s THEN wallet_share END)         AS share_now,
             AVG(CASE WHEN nrf_week BETWEEN %(nrf_week)s - 12 AND %(nrf_week)s - 1
                       THEN wallet_share END)                                     AS share_base,
             AVG(CASE WHEN nrf_week = %(nrf_week)s THEN wallet_share END) -
             AVG(CASE WHEN nrf_week BETWEEN %(nrf_week)s - 12 AND %(nrf_week)s - 1
                       THEN wallet_share END)                                     AS share_delta
      FROM   CURATED.fact_concon_signal
      WHERE  category = %(category)s AND region = %(region)s
      GROUP  BY competitor
      ORDER  BY ABS(share_delta) DESC
      LIMIT  %(top_n)s
    """
    return query(sql, {"category": category, "region": region,
                       "nrf_week": nrf_week, "top_n": top_n})

Most queries against CURATED return aggregated rows — units, revenue, margin. Some UCs need consumer_key joins (e.g., a CSR escalation: "which named customer just abandoned an order"). That's a Tier-3 PII unlock — guarded by explicit consent and audited every call:

# services/rc/rc-wbr/mcp/merml-mcp/src/merml_mcp/auth.py
"""Auth + Tier-3 PII unlock for merml-mcp."""
from __future__ import annotations
from dataclasses import dataclass
from datetime import datetime, timezone
from typing import Any

from fastapi import HTTPException
from msal import ConfidentialClientApplication


@dataclass
class AgentIdentity:
    agent_id: str
    tier: int                        # 1, 2, 3 — increasing PII reach
    tenant: str
    consent_ticket: str | None       # required for tier == 3


def verify_agent_token(authorization: str | None) -> AgentIdentity:
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(401, "missing bearer")
    token = authorization.removeprefix("Bearer ").strip()
    claims = _decode_entra_jwt(token)
    if claims["aud"] != "api://merml-mcp":
        raise HTTPException(401, "wrong audience")
    return AgentIdentity(
        agent_id=claims["agent_id"], tier=claims["tier"],
        tenant=claims["tenant"], consent_ticket=claims.get("consent_ticket"),
    )


def require_tier(identity: AgentIdentity, *, min_tier: int, reason: str) -> None:
    if identity.tier < min_tier:
        raise HTTPException(403, f"tier {min_tier} required: {reason}")
    if min_tier == 3 and not identity.consent_ticket:
        raise HTTPException(403, "tier 3 requires consent_ticket")
    # Always audit a tier-3 unlock
    if min_tier == 3:
        _audit_tier3_unlock(identity, reason)


def _audit_tier3_unlock(identity: AgentIdentity, reason: str) -> None:
    """Write a LEDGER row + Purview audit event for every Tier-3 access."""
    from merml_mcp.ledger import write_ledger_row
    write_ledger_row({
        "ts": datetime.now(timezone.utc).isoformat(),
        "kind": "tier3_pii_unlock",
        "agent_id": identity.agent_id,
        "tenant": identity.tenant,
        "consent_ticket": identity.consent_ticket,
        "reason": reason,
    })

7.2 The Sequential Pattern (Inside The Analyst)

UC-01's main flow has five steps. Inside AnalystRunner.run() they are five method calls — Sequential by construction:

# apex_agentic_merch/runtime/the_analyst.py — Sequential body
def run(self, *, nrf_week: int) -> tuple[dict[str, Any], list[dict[str, Any]]]:
    actuals = self._call("fetch_weekly_actuals_vs_plan", {"nrf_week": nrf_week})  # step 1
    misses  = self._compute_misses(actuals)                                       # step 2
    ranked  = self._call("rank_exceptions_by_severity",                           # step 3

7.3 The Concurrent Pattern (Inside The Finance Lead)

The Finance Lead's four guardrails check independently. Concurrent by declaration:

# apex_agentic_merch/runtime/the_finance_lead.py
"""The Finance Lead — Agent 4. Concurrent guardrail evaluator."""
from __future__ import annotations
import asyncio
from typing import Any
from dataclasses import dataclass


@dataclass
class GuardrailResult:
    id: str
    breached: bool
    actual: float
    threshold: float
    message: str


class FinanceLeadRunner:
    def __init__(self, *, mcp_url: str, manifest: dict[str, Any]) -> None:
        self.mcp_url = mcp_url
        self.manifest = manifest

    async def _otb_buffer(self, ctx: dict[str, Any]) -> GuardrailResult:
        ...

    async def _margin_floor(self, ctx: dict[str, Any]) -> GuardrailResult:
        ...

    async def _markdown_depth(self, ctx: dict[str, Any]) -> GuardrailResult:
        ...

    async def _aggregate_spend(self, ctx: dict[str, Any]) -> GuardrailResult:
        ...

    async def _run_async(self, ctx: dict[str, Any]) -> list[GuardrailResult]:
        # Concurrent — the four checks run in parallel.
        return await asyncio.gather(
            self._otb_buffer(ctx),
            self._margin_floor(ctx),
            self._markdown_depth(ctx),
            self._aggregate_spend(ctx),
        )

    def run(self, **kwargs: Any) -> tuple[dict[str, Any], list[dict[str, Any]]]:
        results = asyncio.run(self._run_async(kwargs))
        breaches = [r for r in results if r.breached]
        ledger_rows = [
            {"kind": "guardrail_check", "id": r.id, "breached": r.breached,
             "actual": r.actual, "threshold": r.threshold}
            for r in results
        ]
        return {
            "all_results": [r.__dict__ for r in results],
            "breach_count": len(breaches),
            "breached_ids": [r.id for r in breaches],
        }, ledger_rows

If any of the four breaches, the journey runner (§7.1) hits the HITL gate. Concurrent + HITL is the architectural answer to Matt King's "101→401" concern: the agent never executes anything destructive without explicit human approval. The Decision Rights framework lives at the gate, not in the prompt.

7.4 The Handoff Pattern (Analyst → Downstream)

Handoff is HTTP fan-out via the routing engine (Chapter 3). The orchestrator wraps it with retries and a per-call audit event:

# apex-m/src/apex_m/orchestrator.py — handoff()
def handoff(self, *, from_agent: str, to_agents: list[str],
            payload: dict[str, Any]) -> dict[str, dict[str, Any]]:
    """Fan out payload from one agent to N downstream agents."""
    results: dict[str, dict[str, Any]] = {}
    for target in to_agents:
        url = self._url_for(target)
        write_audit_event(
            tenant=self.tenant, kind="handoff",
            payload={"from": from_agent, "to": target, "payload_keys": list(payload.keys())},
        )
        with httpx.Client(timeout=self.timeout_s) as c:
            r = c.post(url, json=payload, headers=self._auth_headers())
            r.raise_for_status()
            results[target] = r.json()
    return results

Handoff is point-to-point; the routing engine decides who's downstream. The journey runner stays declarative.

7.5 The Group Chat Pattern (Brief Synthesis)

Brief Synthesis (UC-11/12/13) is a Group Chat. The Briefer is the moderator; UC-11/12/13 contribute Done / Your-Call / Watch bucket items to a shared brief object over multiple rounds. The pattern:

# apex-m/src/apex_m/orchestrator.py — group_chat()
def group_chat(self, *, participants: list[str], seed: dict[str, Any],
               max_rounds: int = 3) -> dict[str, Any]:
    """Multi-round group chat with a shared brief object."""
    brief: dict[str, Any] = {"done": [], "your_call": [], "watch": [], "_rounds": 0}
    for round_no in range(max_rounds):
        brief["_rounds"] = round_no + 1
        for p in participants:
            url = self._url_for(p)
            payload = {"seed": seed, "brief_so_far": brief, "round": round_no}
            with httpx.Client(timeout=self.timeout_s) as c:
                r = c.post(url, json=payload, headers=self._auth_headers())
                contribution = r.json()
            brief = self._merge_contribution(brief, contribution)
        if self._brief_is_done(brief):
            break
    write_audit_event(tenant=self.tenant, kind="group_chat_complete",
                      payload={"rounds": brief["_rounds"], "participants": participants})
    return brief

The moderator (The Briefer) decides when the brief is complete. _brief_is_done() checks invariants: at least one item per bucket, no contradictions, total length within Adaptive Card limits.

7.6 HITL Gates

Every Tier-2+ decision pauses for human approval. APEX-M ships an HITLGate primitive with three resume modes:

# apex-m/src/apex_m/hitl.py — sketch
from __future__ import annotations
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
from typing import Any
from enum import Enum


class Outcome(str, Enum):
    APPROVED = "approved"
    DENIED   = "denied"
    TIMEOUT  = "timeout"


@dataclass
class Decision:
    outcome: Outcome
    approver: str
    note: str
    ts: datetime


@dataclass
class HITLGate:
    persona: str
    approver: str                          # principal resolved from persona_principal_bindings
    response_window_hours: float
    payload: dict[str, Any]
    mode: str = "synchronous"              # "synchronous" | "adaptive_card_callback" | "escalating"

    def wait_for_decision(self) -> Decision:
        deadline = datetime.now(timezone.utc) + timedelta(hours=self.response_window_hours)
        ticket = self._issue_ticket()
        self._notify_approver(ticket)
        return self._poll_until(ticket, deadline)

    def _poll_until(self, ticket: str, deadline: datetime) -> Decision:
        while datetime.now(timezone.utc) < deadline:
            d = self._check_decision(ticket)
            if d is not None:
                return d
            # backoff 1s → 2 → 4 → 8 → 16 → cap 60
            ...
        return Decision(outcome=Outcome.TIMEOUT, approver=self.approver,
                        note="response window elapsed", ts=datetime.now(timezone.utc))

UC-18 (Escalate on no response) fires when Outcome.TIMEOUT hits — promotes to the next approver in the chain. UC-19 (Log decision to LEDGER WORM) writes the Decision with a hash anchored to the prior row.

7.7 The LEDGER Hash Chain

Every persona run, every MCP call, every HITL decision lands in the LEDGER. The append-only table chains by row hash so any tamper after-the-fact is detectable:

-- infra/snowflake/audit/ledger.sql
CREATE TABLE IF NOT EXISTS VUORI_PROD.AUDIT.LEDGER (
    seq         NUMBER          AUTOINCREMENT START 1 INCREMENT 1,
    ts          TIMESTAMP_TZ    DEFAULT CURRENT_TIMESTAMP(),
    agent_id    STRING          NOT NULL,
    kind        STRING          NOT NULL,
    payload     VARIANT,
    prev_hash   STRING,                                    -- hash of seq - 1
    row_hash    STRING          NOT NULL,                  -- SHA256(prev_hash + payload + ts + agent_id)
    correlation STRING                                     -- journey id; ties Friday-to-Monday rows together
);

CREATE OR REPLACE PROCEDURE AUDIT.SP_APPEND_LEDGER(
    p_agent_id    STRING, p_kind STRING, p_payload VARIANT,
    p_correlation STRING
)
RETURNS STRING LANGUAGE SQL AS
$$
DECLARE
    v_prev_hash STRING;
    v_row_hash  STRING;
BEGIN
    SELECT row_hash INTO :v_prev_hash FROM AUDIT.LEDGER ORDER BY seq DESC LIMIT 1;
    v_row_hash := SHA2(CONCAT_WS('|',
        COALESCE(:v_prev_hash, ''), :p_agent_id, :p_kind,
        TO_VARCHAR(:p_payload), TO_VARCHAR(CURRENT_TIMESTAMP())), 256);
    INSERT INTO AUDIT.LEDGER (agent_id, kind, payload, prev_hash, row_hash, correlation)
    VALUES (:p_agent_id, :p_kind, :p_payload, :v_prev_hash, :v_row_hash, :p_correlation);
    RETURN :v_row_hash;
END;
$$;

The harness's ledger_check executor (Chapter 8) walks the chain on every test run. A break anywhere — and the run is RED, regardless of whether the agents' own assertions passed.

8.5 The Stub-then-Graduate Model

Every step ships with a stub. The executor first tries to import using:. If that succeeds, the real agent runs. If the import fails, it falls back to the stub. To graduate a step:

  1. Confirm the real agent exists in apex_agentic_merch.runtime.<persona>.<verb> and is importable.
  2. Edit using: in the step from the generic ...the_analyst.run to a specific verb like ...the_analyst.detect_exception. Specific verbs make failure modes legible.
  3. Run the UC: uv run mvp-harness run UC-01. The stepper UI's badge shows stub when the fallback fired; its absence means the real agent ran.
  4. If the real agent's output differs from the stub, tighten the assertions to match. That's the productive friction — it's where the harness pays for itself.

You can graduate steps incrementally. Mixing real and stub steps within one UC is supported and useful during runtime bring-up.

8.10 The LEDGER Hash Chain Assertion

The ledger_check executor runs the SQL from §7.7 and validates the chain. The assertion:

# MVP/TestHarness/src/mvp_test_harness/assertions/hash_chain.py — sketch
"""Hash chain assertion — walks LEDGER rows for the correlation, recomputes hash per row."""
from __future__ import annotations
import hashlib
from dataclasses import dataclass


@dataclass
class HashChainResult:
    passed: bool
    rows_walked: int
    first_break_seq: int | None
    message: str


def validate_chain(rows: list[dict]) -> HashChainResult:
    if not rows:
        return HashChainResult(passed=True, rows_walked=0, first_break_seq=None,
                               message="empty chain — vacuously valid")
    prev_hash = None
    for row in rows:
        expected = hashlib.sha256(
            "|".join([prev_hash or "", row["agent_id"], row["kind"],
                      row["payload_text"], row["ts_text"]]).encode()
        ).hexdigest()
        if expected != row["row_hash"]:
            return HashChainResult(passed=False, rows_walked=row["seq"],
                                   first_break_seq=row["seq"],
                                   message=f"hash mismatch at seq={row['seq']}")
        prev_hash = row["row_hash"]
    return HashChainResult(passed=True, rows_walked=len(rows),
                           first_break_seq=None, message="chain intact")

If anyone tampers with a LEDGER row post-hoc — even by changing the payload directly in the database — the chain breaks and the assertion fails. The acceptance run becomes Vuori's tamper-evident record.

10.5 OIDC Federation to Azure

No long-lived service principal secrets. Every GitHub workflow that touches Azure exchanges its workload identity token for an Azure access token at job start. The setup is per-environment.

Step 1 · Register an app per substrate

$ az ad app create --display-name "github-vuori-dev"
$ az ad app create --display-name "github-vuori-test"
$ az ad app create --display-name "github-vuori-stage"
$ az ad app create --display-name "github-vuori-prod"

Step 2 · Federate each app to its GitHub Environment

# infra/oidc/federate-stage.sh
#!/usr/bin/env bash
set -euo pipefail

APP_ID="$(az ad app list --display-name 'github-vuori-stage' --query '[0].appId' -o tsv)"

az ad app federated-credential create --id "$APP_ID" --parameters - <<'JSON'
{
  "name": "github-vuori-stage",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:org/apex-framework:environment:stage",
  "audiences": ["api://AzureADTokenExchange"]
}
JSON

# Role assignments — least privilege per substrate.
SUB_ID="$(az account show --query id -o tsv)"
RG="rg-vuori-stage"
az role assignment create --assignee "$APP_ID" \
    --role "Contributor" --scope "/subscriptions/$SUB_ID/resourceGroups/$RG"
az role assignment create --assignee "$APP_ID" \
    --role "Key Vault Secrets User" \
    --scope "/subscriptions/$SUB_ID/resourceGroups/$RG/providers/Microsoft.KeyVault/vaults/kv-vuori-stage"

The federation subject nails the credential to this repo + this environment. A workflow running against dev can never mint a stage token, even if a malicious PR slipped a credential reference.

Step 3 · Store the app IDs as Environment-scoped variables

For each GitHub Environment, add three repository variables:

AZURE_CLIENT_ID         = <app id of github-vuori-<substrate>>
AZURE_TENANT_ID         = <Vuori Entra tenant id>
AZURE_SUBSCRIPTION_ID   = <Vuori Azure subscription id for that substrate>

These are variables, not secrets — the values aren't sensitive. The credential is minted at job time via OIDC.

10.6 Secrets — Sourced From Key Vault

The only thing GitHub stores in Secrets is the OIDC client ID (per §10.5). Everything else — Snowflake connection strings, Anaplan API tokens, Centric ODBC creds, Teams webhook URLs — lives in the per-substrate Key Vault and is pulled at job start.

# .github/workflows/deploy.yml — secret fetch step
- name: Azure login (OIDC)

    client-id: ${{ vars.AZURE_CLIENT_ID }}
    tenant-id: ${{ vars.AZURE_TENANT_ID }}

- name: Fetch Snowflake account from Key Vault

10.10 Tying It Back to the Wizard

The wizard knows about substrates because of the use-case YAML's substrate: field (Chapter 2). The CI flow knows because of the GitHub Environment. The two are wired together at deploy time:

1. CI checks out main.
2. Reads services/rc/rc-wbr/use-cases/vuori/use-case.yaml.
3. Confirms the YAML's substrate field matches the GitHub Environment being deployed to.
4. Calls `python apex.py validate` to confirm A1-A4 are still green.

6. Polls /api/security-gate?tenant=<tenant> until all 15 are GREEN.
7. POSTs to /api/deployments — wizard handles Bicep what-if + apply + LEDGER audit.

A substrate mismatch (e.g., YAML says stage, workflow is targeting prod) is caught at step 3 and fails the deploy before anything touches Azure. The wizard is the gatekeeper; the workflow is the conveyor.

11.4 The Reusable Deploy Workflow

Every substrate calls the same workflow. The difference is the Environment name and the input parameters.

# .github/workflows/deploy.yml — reusable
name: deploy
on:
  workflow_call:
    inputs:
      substrate:    { required: true,  type: string }
      image_tag:    { required: true,  type: string }
      use_case_id:  { required: false, type: string, default: vuori }
      confirm_destructive:
        required: false
        type: boolean
        default: false

permissions:
  id-token: write
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    environment: ${{ inputs.substrate }}
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v3
      - run: uv sync --frozen

      - name: Azure login (OIDC)
        uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Substrate-mismatch guard
        run: |
          YAML_SUBSTRATE=$(uv run python - <<'PY'
          import yaml, sys
          d = yaml.safe_load(open("services/rc/rc-wbr/use-cases/${{ inputs.use_case_id }}/use-case.yaml"))
          print(d["substrate"])
          PY)
          if [ "$YAML_SUBSTRATE" != "${{ inputs.substrate }}" ]; then
              echo "::error::use-case.yaml says $YAML_SUBSTRATE but workflow targets ${{ inputs.substrate }}"
              exit 1
          fi

      - name: Boot the wizard (headless)
        run: |
          uv run python apex.py launch --no-frontend &
          sleep 3

      - name: PSG · all 15 gates with context
        id: psg
        run: |
          curl -sf -X POST http://localhost:8000/api/security-gate/with-context \
               -H 'Content-Type: application/json' \
               -d '{"tenant":"vuori-${{ inputs.substrate }}","service_code":"rc-wbr",
                    "use_case_id":"${{ inputs.use_case_id }}","substrate":"${{ inputs.substrate }}"}' \
               | tee psg.json
          test "$(jq -r '.summary' psg.json | grep -c '15 of 15 GREEN')" = "1"

      - name: Validate user-acceptance criteria
        run: uv run python tools/validate_acceptance.py

  render-and-whatif:
    needs: validate
    runs-on: ubuntu-latest
    environment: ${{ inputs.substrate }}
    outputs:
      destructive: ${{ steps.whatif.outputs.destructive }}
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Render Bicep params via wizard
        run: |
          curl -sf -X POST http://localhost:8000/api/deployments/render \
               -H 'Content-Type: application/json' \
               -d '{"tenant":"vuori-${{ inputs.substrate }}","service_code":"rc-wbr",
                    "use_case_id":"${{ inputs.use_case_id }}",
                    "substrate":"${{ inputs.substrate }}","wave":"w2"}' \
               > rendered-params.json

      - name: Bicep what-if
        id: whatif
        run: |
          az deployment group what-if \
              -g rg-vuori-${{ inputs.substrate }} \
              -f apex-m/infra/bicep/blueprints/w2-pilot.bicep \
              -p @rendered-params.json \
              -o json > whatif.json
          if jq -e '.changes[] | select(.changeType == "Delete")' whatif.json > /dev/null; then
              echo "destructive=true" >> "$GITHUB_OUTPUT"
          else
              echo "destructive=false" >> "$GITHUB_OUTPUT"
          fi

      - name: Upload what-if artefact
        uses: actions/upload-artifact@v4
        with: { name: whatif-${{ inputs.substrate }}, path: whatif.json }

  apply:
    needs: render-and-whatif
    runs-on: ubuntu-latest
    environment: ${{ inputs.substrate }}        # ← gate: reviewers enforced here
    steps:
      - name: Refuse destructive without confirm
        if: needs.render-and-whatif.outputs.destructive == 'true' && inputs.confirm_destructive != true
        run: |
          echo "::error::destructive changes detected; re-run with confirm_destructive=true"
          exit 1

      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      - name: Deploy via wizard
        run: |
          curl -sf -X POST http://localhost:8000/api/deployments \
               -H 'Content-Type: application/json' \
               -d '{"tenant":"vuori-${{ inputs.substrate }}","service_code":"rc-wbr",
                    "use_case_id":"${{ inputs.use_case_id }}","substrate":"${{ inputs.substrate }}",
                    "image_tag":"${{ inputs.image_tag }}",
                    "note":"confirm_destructive=${{ inputs.confirm_destructive }}"}'

Three jobs: validate (PSG + acceptance), render-and-whatif (Bicep render + what-if + destructive detection), apply (the actual deploy through the wizard). Each gates the next via needs:. The environment-level reviewers fire on the apply job — that's where the human approval lands.

11.6 The Drift-Detection Cron

# .github/workflows/drift-cron.yml
name: drift-cron
on:
  schedule:
    - cron: "0 6 * * *"        # 06:00 UTC daily
  workflow_dispatch:

permissions: { id-token: write, contents: read, issues: write }

jobs:
  scan:
    strategy:
      matrix:
        substrate: [dev, test, stage, prod]
    runs-on: ubuntu-latest
    environment: ${{ matrix.substrate }}
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Run drift detector
        id: drift
        run: |
          uv run python apex.py launch --no-frontend &
          sleep 3
          curl -sf http://localhost:8000/api/drift/vuori-${{ matrix.substrate }} \
               > drift.json
          SEVERITY=$(jq -r '.severity' drift.json)
          echo "severity=$SEVERITY" >> "$GITHUB_OUTPUT"
      - name: File issue on medium/high drift
        if: steps.drift.outputs.severity != 'low'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const drift = JSON.parse(fs.readFileSync('drift.json', 'utf8'));
            github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Drift detected on ${{ matrix.substrate }} — ${drift.severity}`,
              body: '```json\n' + JSON.stringify(drift, null, 2) + '\n```',
              labels: ['drift', '${{ matrix.substrate }}', drift.severity],
            });

Every morning at 06:00 UTC, drift runs across all four cloud substrates. Anything beyond low opens an issue with the diff embedded. The Tech Lead triages at the daily stand-up.

11.7 The Rollback Playbook

The fastest rollback is a redeploy of the prior tag — the same workflow, different image_tag. The procedure, in priority order:

  1. Identify the last known good tag. gh release list --repo org/apex-framework — pick the most recent v* before the bad change.
  2. Re-trigger deploy-prod. gh workflow run deploy-prod.yml --ref v0.10.0 -f image_tag=v0.10.0. Same approval path; same PSG gates; same destructive-change confirm.
  3. Wait for green. Confirm the deployment record in the wizard at /history. Confirm the LEDGER row lands with the new correlation ID.
  4. If rollback also fails: the data layer is the issue, not the agents. Switch The Briefer to "watch-bucket only" mode via the per-client manifest (set agents.the_briefer_url to the no-op stub URL). Brief still ships; the agents stop acting.
  5. File a retro item. A failed rollback is a Sev-2 retro topic at the next sprint retrospective.

Tested quarterly. Every quarter, the team picks an arbitrary day in the last 30 and rolls prod back to it, then forward to current. The first time it surfaces something unexpected; subsequent quarterly drills are confidence-building.

  • One reusable deploy workflow drives all four substrates. Per-substrate wrappers attach the GitHub Environment that carries the reviewers, the OIDC credential, and the wait timer.
