SECURITY REFERENCE

APEX Security

How a domain-canonical agentic framework keeps client data inside the client's tenant, every decision traceable to a human, and every audit row immutable — built end-to-end on Microsoft-native infrastructure.

Framework APEX Core v1.2 · Agentic Platform for Enterprise eXecution
Substrate Microsoft Entra · Fabric · Purview · Azure AI · Logic Apps
Source of truth APEX Developer Guide · Companion 05
Posture Independence-safe · client-tenant data planes
The thesis. APEX bakes observability and security into the contract, not bolts them on — every agent invocation is a traceable operation under one operation_Id, every data access is governed by managed identity + OneLake path-ACL + Purview label, and every decision is signed by an Entra-authenticated human.
01 · ARCHITECTURE & DEPLOYMENT

Deployment topology

APEX has two clearly separated trust zones — a Deloitte-owned authoring zone that produces signed framework artifacts and never holds client data, and the client Azure tenant where every runtime component, every byte of client data, every audit row, and every encryption key lives.

Deloitte authoring zone (no client data) Client Azure tenant boundary Agent runtime (managed identity) Decision gate · HITL surface Audit · provenance

Reading the diagram

  • Two trust zones, one signed boundary. Deloitte authors APEX (top); client deploys it (bottom). The only thing that crosses is a signed manifest bundle pulled GitOps-style — never client data going up, never Deloitte secrets coming down.
  • Data flow is left-to-right inside the tenant. Sources → Bronze → Silver → Gold. Tokenisation happens at the Bronze→Silver boundary — cleartext PII never reaches Silver, Gold, or any agent.
  • Decision flow is bottom-to-top. Agent reasons → MCP tool calls Fabric (tokens only) → Logic Apps orchestrates → Teams prompts a human → audit row written.
  • Cross-cutting controls run alongside everything. Entra authenticates every actor, Purview labels and DLP-blocks every data egress, App Insights traces every span, Key Vault holds the CMK, Defender watches the posture.
The bottom line. Every component above is a Microsoft-managed service or a workload running on one — no Deloitte-hosted middleware, no parallel security plane. If the client's Azure tenant is governed to Microsoft's Well-Architected baseline, APEX inherits that posture for free.
02 · DATA SOVEREIGNTY

Where does our data live?

APEX is a framework, not a product. Clients deploy APEX-shaped solutions on their own Microsoft infrastructure. There is no Deloitte-side runtime, no Deloitte-side retention, and no shared multi-tenant control plane.

The Independence posture, in three rules

RULE 1

Client-tenant data planes

Every byte of client data lives inside the client's Azure tenant — Bronze/Silver/Gold lakehouses, the audit log, PII tokens, decision records. Deloitte does not host an APEX runtime.

RULE 2

Client-issued identities

Deloitte personnel deploying or operating APEX use client-issued Entra identities, not Deloitte service principals. The client's IAM is the audit boundary.

RULE 3

No client identity in code

The PRACTICE-ACCOUNT-ID validation rule enforces opaque account IDs in shipped artifacts — client identity stays out of Deloitte-owned source and logs.

The identity model — three classes, one picture

Every authenticated action in APEX falls into exactly one of three identity classes. Each class has a different threat model and a different audit footprint.

Per-tenant identity segregation (belt-and-suspenders)

Each L4 tenant gets its own managed identity — mi-apex-<tenant>-mcp-read. So even if the header-based tenant scoping ever broke, the identity itself cannot read another tenant's data: OneLake path-ACLs deny the token before the query reaches the SQL engine.

The bottom line. Data sovereignty in APEX is enforced at three independent layers — tenant Entra boundary, OneLake path-ACL, and per-tenant managed identity — and checked by a CI lint rule that fails the build on any cross-tenant code path.
03 · DECISION INTEGRITY

What if an agent goes wrong?

Every APEX orchestration declares — at design time, in the manifest — which decisions need a human, which need an acknowledgement, and which can run zero-touch. There is no implicit autonomy.

The gate taxonomy

Every agent and every orchestration carries an explicit gate_kind. The runtime refuses to execute an unannotated decision path.

Gate kind What it means Where it shows up Who decides
HITL Human approval required before the action commits. Teams Adaptive Card · timeout per service SLO Entra-authenticated approver (recorded in audit)
ACK_ONLY Action runs; a human acknowledges within a window or it escalates. Teams notification + ack button Designated owner (operator, manager, etc.)
ZERO_TOUCH Fully autonomous — but only after a manifest review approved the gate-kind during release. Logged but not surfaced to a human The manifest itself (signed at release time)
ESCALATION Auto-promoted to a higher approver when the primary times out or breaches policy. Teams escalation channel · paging Higher-tier approver with audit trail

Three layers of "if it goes wrong"

1. The gate stops it

For HITL gates, no commit happens until a human says yes — recorded as an Entra decider_oid on the gate span.

2. The rollback pointer reverses it

Every state-changing orchestration writes a rollback_pointer — the ID of a compensating orchestration. Reversible within 7 days for most services.

3. The DLP gate blocks the leak

Even if an agent tries to return cleartext PII in an outbound response, Purview DLP returns -32003 DLP_VIOLATION instead of the data.

The decision audit row

Every HITL approval writes one row to silver_decision_audit. The row includes:

  • The full operation_Id tree pointer (so the decision is reconstructable)
  • The decider's Entra oid — that is the electronic signature for FDA 21 CFR Part 11
  • SHA-256 hash of the input the human saw, and of the output that committed
  • The rollback_pointer if reversal is in scope
The bottom line. "Agent went rogue" stories do not apply to APEX the way they apply to ad-hoc deployments. The gate is part of the contract, not a runtime decoration — and the manifest validator refuses to ship any agent or orchestration without one.

Where the audit lives — and stays

Append-only

The silver_decision_audit table is append-only by ACL — no UPDATE, no DELETE. The MI that writes audit rows cannot modify them.

Customer-managed keys

Encrypted with Fabric CMK, key in the client's Azure Key Vault. Even Deloitte personnel operating the engagement cannot read the audit log without client-issued role assignment.

Retention by practice

7 years for HLS/ER (HIPAA / FERC / 21 CFR Part 11), 5 years for RC/AXLE/TH/TMT/ICE — unless a regulation pins it longer. Monthly Purview audit reports auto-delivered to compliance officers.

The bottom line. "Show me what this agent did last Tuesday at 2:14 PM" is a single KQL query. For a forensic investigator, the entire decision chain — including the human signature — reconstructs from one operation_Id.

The PII regime in plain English

Cleartext PII never crosses Bronze→Silver

Tokenisation is contractual at the medallion boundary, enforced by the manifest validator. Any pipeline that violates the contract fails CI.

Tokens are stable

The same cleartext maps to the same token across invocations — joins still work; the cleartext does not need to be rehydrated to do the work.

Reverse-tokenisation is audited

Requires mi-apex-<practice>-pii-unlock and emits an audit row on every call. Agents never reverse-tokenise; pipelines do, narrowly.

The bottom line. The right-to-erasure replay pattern handles the hard case — when the row is still within regulatory retention but the customer has exercised erasure. APEX re-tokenises with an unrelated token, tombstones the original, and replays the last 30 days of orchestrations that touched it. Documented step-by-step.

07 · FAQ

Frequently asked questions

The questions experienced enterprise security teams reach for first. If yours isn't here, the dev-guide companion linked at the bottom of the page goes deeper.

Q1"Could a malicious prompt trick an agent into exfiltrating PII?"
Three independent layers say no. (1) Agents read tokens, not cleartext — the tokeniser sits at the Silver boundary. (2) The MCP tool that returns customer-impacting fields checks the consent flag before it returns even the token. (3) Purview DLP on the outbound channel returns -32003 DLP_VIOLATION if cleartext PII appears in any outgoing response. All three layers must fail simultaneously for an exfiltration to land.
Q2"Who can read the audit log? Can Deloitte personnel read it?"
Only identities the client grants mi-apex-*-observability read role to. Deloitte personnel operating an engagement use client-issued identities; the role assignment is controlled by client IAM. The audit table is encrypted with a CMK in the client's Key Vault — even if Deloitte's storage subscription were compromised, the audit ciphertext is unreadable without the client's key.
Q3"What stops an agent from running in zero-touch mode for a decision that should require a human?"
The manifest validator. Every agent and orchestration declares gate_kind at design time; validate-manifest.js fails the build if a state-changing orchestration ships with ZERO_TOUCH outside the allow-list. Promotion from HITL → ACK_ONLY → ZERO_TOUCH is a manifest change reviewed and signed at release time, not a runtime toggle.
Q4"How does GDPR right-to-erasure work when records are still in regulatory retention?"
The replay pattern: tokenizer-mcp.reverse_lookup finds the stable token (audited). Rows past retention are deleted in place. Rows still under retention are re-tokenised with an unrelated token and the original token is tombstoned. The last 30 days of affected orchestrations replay to confirm no decision output depends on the now-erased cleartext. Erasure itself is logged with a retention-exempt flag.
Q5"What is the blast radius of a compromised managed identity?"
Bounded by three things: (a) the role assignment scope — typically per-tenant, per-practice, single-purpose; (b) OneLake path-ACL — even with a valid token, the MI can only read paths it is granted; (c) the per-tenant MI variant (mi-apex-<tenant>-mcp-read) cannot reach another tenant's lakehouse. Rotation is handled by Entra; revocation is immediate.
