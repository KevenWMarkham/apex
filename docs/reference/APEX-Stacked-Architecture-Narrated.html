Layer 01 · Foundation · Cross-cutting

Identity & Trust — always on, always underneath

Entra gives every agent a managed identity. Purview propagates classification and lineage through every layer above. These two planes are not optional; they are the reason APEX decisions survive regulatory inspection.

Microsoft Entra · Identity Plane

The agent cannot reach what the identity does not authorize

Every agent in APEX runs under a managed identity. Entra is where those identities are issued, scoped, governed, and audited. The architectural principle — an agent is a first-class security principal, not a shared service account.

  • Managed identities (system-assigned & user-assigned) for every agent workload — no stored secrets, no rotating keys.
  • Conditional Access applies to agent sign-ins the same way it applies to humans: location, device posture, risk score, MFA.
  • Workload identity federation — agents running outside Azure authenticate without passwords via OIDC token exchange.
  • Scoped permissions via app roles + On-Behalf-Of (OBO) flows so the agent inherits the caller’s authorization, not a superset of it.
  • Privileged Identity Management for time-bounded elevation when an agent must act on sensitive corpus.
  • Audit trail — every sign-in, token issuance, and permission grant is a Microsoft Entra audit log record.

Microsoft Purview · Trust Plane

Classifications propagate; lineage is end-to-end

Purview is the classification, DLP, catalog, and lineage spine. Classifications applied at Silver tokenization propagate through Gold views, MCP tool outputs, agent reasoning traces, and audit rows — without application-layer rewrites.

  • Sensitivity labels — Public, Internal, Confidential, Highly Confidential flow end-to-end.
  • Classification taxonomies — PII, PHI, PCI, SOX, SupplierConfidential, CommercialSensitive, TradeSecret.
  • DLP policies enforced at the Fabric edge — agents physically cannot export what DLP denies.
  • Unified Catalog — business-glossary terms bound to canonical entities; the vocabulary is governed, not scattered.
  • End-to-end lineage across Bronze → Silver → Gold → MCP → Foundry agent → Copilot output.
  • Purview Compliance Manager — regulatory controls (HIPAA, SOX, PCI-DSS, GDPR) mapped to evidence in Fabric / Foundry.

Layer 02 · Data Plane · Microsoft Fabric

One lake. Three tiers. Agent-safe on the way up.

OneLake is the single physical home. The medallion architecture is non-negotiable. Bronze is raw, Silver is canonical, Gold is agent-safe. Agents never touch Bronze or Silver directly.

OneLake — the unified lakehouse

No cross-platform replication · no synchronization drift

Every APEX artifact — Bronze table, Silver model, Gold view, semantic model, notebook output — lives in OneLake. Delta-Parquet under the hood. One copy of truth, referenced everywhere via Shortcuts.

  • Delta Parquet storage — ACID transactions, time travel, versioning.
  • Shortcuts reference data in other OneLake workspaces, ADLS Gen2, Amazon S3, Google Cloud Storage, Dataverse — without copying.
  • Single physical home means a canonical entity appears exactly once, consumed by every downstream service.
  • Direct Lake mode serves OneLake tables to Power BI and MCP tools at sub-second latency with zero data duplication.

What each tier owns, what it forbids
Source systems → Bronze → Silver → Gold → MCP tool → Foundry agent

Bronze

Raw · SOR-fidelity · immutable

System-of-record-fidelity copies brought in exactly as emitted. Preserves forensic truth.

  • Mirrored Databases — CDC from SAP, Salesforce, Dataverse, Snowflake, SQL MI without ETL authoring.
  • Pipelines for batch file and REST ingestion.
  • Dataflows Gen2 for low-code transforms from legacy sources.
  • Eventstream for real-time telematics, OT, IoT, and change feeds.
  • Immutable, versioned, time-travel enabled — supports post-mortem and regulator lookback.
  • Purview scans label at origin so classifications start here, not downstream.

Silver

Canonical · conformed · classified

Raw becomes canonical. Conformed to the Practice’s schemas (SCML, PatientML, AXLEML…). PII is tokenized here.

  • Conforming to canonical — Silver tables match the Practice schema exactly, regardless of source system idiosyncrasy.
  • PII tokenization at Silver — once, platform-level; Gold and above never see raw PII.
  • Slowly-changing-dimension (SCD2) handling, deduplication, referential integrity.
  • Classification attachment — sensitivity labels applied column-by-column from the Practice schema manifest.
  • Business-rule enforcement — data-quality tests, null-checks, and ISO 8000-style validations gate Silver writes.

Gold

Agent-safe · identity-scoped · output-signed

The only tier agents see. Views are identity-scoped, classification-aware, output-signed, manifest-registered.

  • One Gold view ↔ one MCP tool. No untyped surface.
  • Row-level security via Entra managed identity; column-level masking via Purview sensitivity label.
  • Output signed with the Gold-view manifest hash — audit rows bind the exact view version consulted.
  • Direct Lake serves to Power BI, Copilot, MCP tools with sub-second latency.
  • Pre-measure derivations (stock-days-remaining, days-since-last-encounter, RUL) materialized here.

Layer 03 · Canonical Schema Layer

The acceleration kernel

A canonical schema is not a database schema. It is a semantic contract — a typed, classification-aware specification of the entities, relationships, and derivations that matter in a Practice. Every new agentic use case inherits entities instead of re-authoring them.

What a canonical schema specifies

Seven things · enforced in code, governance, and agent behavior
  • Entities that matter — SKU, Category, Store, Customer, Patient, Encounter, Well, Station, Subscriber, Traveler, Machine.
  • Attributes each entity carries — typed, with defaults, nullability rules, and allowed value sets.
  • Relationships between entities — cardinality, temporal validity, foreign-key paths.
  • Classifications that apply — PII, PHI, PCI, SOX, SupplierConfidential, TradeSecret.
  • Business-term bindings in Purview Unified Catalog — governed vocabulary, not scattered glossaries.
  • Pre-measure derivations — computed columns like stock-days-remaining, days-since-last-encounter, RUL (Remaining Useful Life).
  • Post-measure definitions — DAX / SQL / KQL for period-over-period, rolling-window, attribution calculations.

The contract is enforced in three places: in code (Fabric artifacts conform to it), in governance (Purview labels derive from it), and in agent behavior (MCP tool bindings expose it).

Six reasons agentic AI benefits categorically more from canonical schema than BI

Traditional BI gains a little; agents gain everything
01

Agents reason across entities

A BI dashboard visualizes one entity at a time. An agent routinely reasons across 5–10 entities in a single decision. Without canonical relationships, the agent must do its own join-logic — slow, error-prone, non-auditable.

02

Agents need typed interfaces

A human BI user can resolve ambiguity ("is this price pre-tax?"). An agent cannot. Typed schema contracts are mandatory for agent reliability, not nice-to-have.

03

Agents run at volume

Thousands of decisions per day across a production fleet. Schema stability is the substrate of reproducible behavior — drift at Silver cascades into unbounded variance at the agent.

04

Classification must propagate

PII and PHI cannot be inferred — they must be declared. Canonical schema carries the classification by column so Gold, MCP, and audit rows all inherit it automatically.

05

Agent evaluation requires stability

Testing across 10,000 synthetic scenarios requires the schema those scenarios are expressed against to be consistent. Without canonical schema, systematic improvement is impossible.

06

Cross-Practice reasoning needs federation

Diversified clients reason across Practice boundaries — an employee who is also a customer, an equipment failure whose warranty crosses Practice SORs. Ad-hoc semantics cannot federate.

§1.6A · Industry Standards Foundation

APEX schemas are not invented from scratch

Each canonical schema is designed on top of the industry standards that already govern its vertical. Clients keep their standards investment. Regulators recognize outputs as evidentiary-grade by design.

Why standards matter — three reasons

The argument for building on top, not around
  • Client investment preservation — an SAP item master already conformant to GS1 GTIN, a Salesforce Commerce Cloud catalog already conformant to Schema.org, an EDI X12 inbound already compliant — all integrate to SCML through off-the-shelf APEX adapters, not custom engineering.
  • Regulatory recognition — outputs conforming to HL7 FHIR, CDISC SDTM, IEC 61850, or NERC CIP evidence schemas are recognized by regulators as compliance artifacts, not as something-requiring-translation.
  • Cross-vendor interop — the client keeps the freedom to swap SORs without rewriting the canonical layer; the schema speaks the standard, not the vendor.

Layers 04 · 05 · 06 · MCP · Foundry · Orchestration

Where agents reason, reversibly

Between data and decision sits three layers: the MCP tool binding that agents call; the Foundry reasoning plane where agents run; and the orchestration layer that composes agents into service outcomes.

MCP tool binding — the contract surface

Layer 04 · one typed tool per Gold view · nothing else is callable

Agents cannot touch Bronze or Silver. They call MCP tools — hosted in Azure Container Apps or Azure Functions — that front identity-scoped, classification-aware Gold views. The tool contract is model-agnostic, typed, and manifest-registered.

  • Typed input / output — tools expose an OpenAPI-style contract the agent can validate.
  • Identity-scoped — tools verify OBO tokens; row-level security is enforced here, not in the agent.
  • Classification-aware — column masking applied at the tool edge per Purview sensitivity label.
  • Manifest-registered — discoverable by authorized agents; untrusted agents cannot enumerate unused tools.
  • Hosted in Azure Container Apps (stateful tools) or Azure Functions (stateless lookup tools).
  • Model-agnostic — works with any agent runtime that speaks MCP: Foundry, Semantic Kernel, Copilot Studio, or future runtimes.

What “context” means for an agent

Three sources · one hybrid model

A production APEX agent assembles its working context from three distinct sources — each with a different governance profile and each addressing a different class of question.

Source 01 · Structured

Canonical schema via MCP

Typed entity reads through MCP tools. One tool per Gold view. Answers questions like “what is the inventory position of SKU X at Store 100 right now?”

  • Classification-aware at the tool edge
  • Identity-scoped by Entra OBO
  • Typed output; agent cannot misinterpret
  • Pinned to manifest + Gold-view version
Source 02 · Semantic

Vector retrieval · episodic memory

Similarity search across curated corpora (SOPs, prior decisions, clinical guidelines, service manuals). Answers questions like “have we seen this failure pattern before?”

  • Azure AI Search + embedding index
  • Corpora classified & labeled by Purview
  • Episodic memory: prior decisions by this acting identity
  • Retrieval scores captured in the audit row
Source 03 · Documentary

File-first attachment (§6.12)

Full documents attached to reasoning context without RAG intermediation. Answers questions like “given this specific contract, is this clause a breach?”

  • LEDGER document lineage preserves provenance
  • File hash + version pinned in the audit row
  • Used for contracts, clinical notes, engineering specs
  • Complements — does not replace — RAG
“The hybrid context model is the governance discipline of knowing which source answers which question. Structured for facts, semantic for precedent, file-first for ground truth. Every APEX agent manifest declares the sources it is allowed to consult — and every audit row records which sources it did.” §6.12 · hybrid context model

File-first context · §6.12

When documents are the ground truth, not the corpus to search

RAG works well when the right answer is somewhere in a large library. File-first works when the right answer is in this specific document. APEX supports both because enterprise agents see both shapes of question daily.

When file-first beats RAG

Ground-truth documents
  • Contract review — the clause in question lives in this contract, not “similar” ones.
  • Clinical decision — the patient’s chart is the authoritative record; similarity is misleading.
  • Engineering change — the ECN, the BOM diff, and the PPAP submission are individually authoritative.
  • Audit response — regulator asks about a specific policy; the specific policy text must be consulted.

Why RAG alone is insufficient

Similarity is not identity
  • RAG returns the k-most-similar chunks — not necessarily the authoritative source.
  • Chunking boundaries can split clauses, sections, or clinical observations mid-thought.
  • Classification labels attached to a document are easily lost when the document is fragmented.
  • Document version drift across an index is invisible at retrieval time.
  • For evidentiary-grade decisions, you need the exact file version — that’s LEDGER’s job.

What LEDGER tracks · field-by-field

Every field has a governance purpose
01 · Identity
Content hash + ledger_ref
Two keys for every document: content-addressable SHA-256 (what the bytes are) and LEDGER record id (this specific ingestion event). Separates what from when.
02 · Provenance
Source + retrieval timestamp
Which system, which URI, when retrieved. A document from SharePoint today is a different provenance record than the same document emailed in tomorrow.
03 · Version chain
Supersedes · superseded_by
Linked-list version graph. Decisions made against v4.1 remain traceable after v4.2 publishes; the chain shows which version drove which decision.
04 · Classification
Purview label + retention
Sensitivity label, declared classifications (PII, PHI, PCI, CommercialSensitive), retention horizon. These travel with every attach event — no re-inference downstream.
05 · Lineage
Derives_from · references
Cross-document relationships. A redline derives_from its source; an impact analysis references supporting docs. Graph-traversable for impact assessment.
06 · Attach events
decision_id · identity · bytes
Every time an agent attaches this document to context, an event is logged — bound to a specific decision_id, acting identity, and how many bytes entered the context window.
07 · Attestation
Signed LEDGER record
ECDSA-signed by the LEDGER service. Tamper-evident. A regulator’s “prove this document was at this version when the decision was made” question has a cryptographic answer.
08 · Audit binding
ledger_ref ↔ decision_id
The audit row stores ledger_ref + content hash for every attached document. The backward chain lets you reconstruct, from any decision, every document version that shaped it.

Parent-child orchestration · §6.13

Agents compose by delegation — state carried through the control plane

A parent agent decomposes a task, spawns child agents, synthesizes their outputs, and writes one audit row that chains to theirs by parent decision ID. The pattern — not monolithic — is how APEX avoids the “one agent does everything” anti-pattern.

Parent · Orchestrator agent↓
├─ Control Plane · Redis ← session + manifest + sub-agent outputs
├─ Child A · Specialist ↔ MCP tool
├─ Child B · Specialist ↔ MCP tool
└─ Child C · Specialist ↔ MCP tool
↑ parent synthesizes → writes audit row → HITL gate (if contracted)

Delegation is typed: parent and child agree on an input schema and an output schema, verified at the control plane. This is why the Trend ID agent (A2) sub-agent decomposition in the Nike R2R engagement was backtestable in isolation — each child had a typed contract independent of the parent composition.

The six envelopes · §2.2A

How commercial, scope, data, schema, trust, and cost nest and reinforce

Commercial contains Scope contains Data — those three nest as concentric boxes. Schema is derived from, not contained by, Data. Trust governs Schema from above. Cost is the sixth — the FinOps envelope that every runtime decision burns against.

Commercial envelope
money & time boundary — Wave 1 $500K–$2M / Wave 2 $5–15M / Wave 3 $8–30M
Scope envelope
functional-scope boundary — which services, agents, tools, Gold views, KPIs
Data envelope
what the agent may read & write — enforced at MCP tool + Purview + Entra
Schema envelope · derives Data
the canonical-entity subset the service depends on — SCML/MERML/CXML for RC-E2E-03, etc.
Trust envelope · governs all above
classification + identity + DLP + HITL — propagates down through every envelope
Cost envelope · the FinOps boundary
tokens · Fabric CU · MCP invocations · storage · network egress — metered per service_code, bound to cost_per_decision on the audit row. Service P&L is a query, not a reconciliation.

When an agent executes a single tool call in production, all six envelopes apply simultaneously: the call must fit the commercial envelope (paid for), be in the scope envelope (approved), return data inside the data envelope (identity-authorized), reference entities inside the schema envelope (canonical-defined), be governed by the trust envelope (classification-appropriate, HITL-correct), and its cost must fit the cost envelope (within token-budget and CU-budget for this service_code). Break any envelope, break the decision.

§1.1A · Seven industry Practices · one pattern

Seven Practices. Five reusable assets each.

A Practice is not what the client buys — it is the internal Deloitte asset that accelerates delivery. Every Practice is a bundle of five things: canonical schemas, agent catalog, orchestration catalog, service catalog, and delivery playbook.

The five reusable assets — every Practice

Why a Practice exists · time-to-value compression
1 · Canonical schemas
Semantic models that normalize the Practice’s domain regardless of the client’s source systems. Built on industry standards.
2 · Agent catalog
Pre-built, tested, governance-wrapped agents addressing the Practice’s top decisions. RC ~40 · HLS ~35 · AXLE ~30 · ER / TMT / TH / ICE 20–30 each.
3 · Orchestration catalog
~15–25 concrete orchestrations per Practice, assembled from the 47 APEX archetypes (sequential · parallel · hierarchical · feedback).
4 · Service catalog
Named, productized services with defined personas, KPIs, SLOs, and commercial envelopes. This is what the client buys.
5 · Delivery playbook
Wave 1 / 2 / 3 sizing, discovery prompts, objection handlers, reference-architecture sketches, pre-clearance checklists — Practice-specific.

The acceleration argument

Why a Practice exists at all

Without a Practice, every client engagement begins from a blank Fabric workspace, a blank Foundry project, and a blank Power BI tenant. The first twelve to eighteen months are spent building the semantic model, agent catalog, orchestrations, service definitions, and delivery method.

A Practice collapses this work. The client inherits Deloitte’s engineering-year investment on day one. Deloitte delivers the first outcome in Wave 1 (4–12 weeks) rather than Wave 2 or 3. That is why a Practice exists: time-to-value compression.
