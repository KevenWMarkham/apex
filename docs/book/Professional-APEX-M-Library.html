What APEX Is — read this first

APEX is a framework that accelerates the building of services and agents on the Microsoft Platform. It is the architectural substrate Deloitte's Microsoft practice uses internally — the medallion data plane in Microsoft Fabric, the MCP tool catalog, the LEDGER hash chain anchored to Microsoft.KeyVault HSM, the agent runtime contract, the orchestration parity between n8n and Azure Logic Apps Hybrid, the trust envelope and identity model on Microsoft Entra ID — to deliver Services faster, more consistently, and with more rigorous governance than rebuilding from raw components each engagement.

APEX is not a product and is not sold to clients. What clients buy are Services — the 38-Service catalog (RC-E2E-03 · HLS-E2E-04 · TMT-TEL-RAA-04 · etc.), each a productized envelope with a KPI commitment, scope, persona model, and two-contract Independence-compliant commercial structure (client ↔ Microsoft for platform, client ↔ Deloitte for the Service-delivery engagement). The Service is the contractable unit; the framework is the means.

How to read the trilogy through this lens: the Sellers Guide teaches sellers to position APEX-accelerated Services to anchor accounts. The Services Guide teaches Service architects to use the APEX framework primitives to build those Services. The Deployment Guide teaches delivery teams to deploy Services on the Microsoft Platform via APEX-accelerated Bicep, agent images, and orchestration. None of the three volumes is selling APEX; all three are about Services that the framework makes possible.

Why a companion, not a fourth Trilogy volume?

The Trilogy partitions the full engagement lifecycle by audience: sellers position, architects design, delivery leads deploy. Each Trilogy volume is generic — it teaches the framework primitives that apply to every Service, every tenant.

The Implementation Guide is the opposite — one Service, one tenant, end-to-end. It is engineering-deep and engagement-narrow. Promoting it to a Trilogy volume would conflate a worked example with reusable framework content, and the firewall between general framework guidance and client-specific implementation matters for Independence posture and confidentiality.

The Library holds both. The Trilogy is the doctrine; the Companion is the case study.

A Note on Independence

All three volumes share the same Independence posture, enforced both stylistically (language) and structurally (architecture). The trilogy says it once below for the reader who lands here first.

Independence — the two-contract model

Across the three volumes the Deloitte–Microsoft delivery relationship is described as "Deloitte's Microsoft practice," "DMTSP," "Microsoft platform capabilities," or "Microsoft-native deployment." Never partner, alliance, or strategic alliance. The two-contract structure — client ↔ Microsoft for the platform, client ↔ Deloitte for services, ECIF flowing direct from Microsoft — is enforced architecturally by: the two Container Registries (Volume III §1.4), the per-tenant Microsoft Fabric workspace (Volume II §8.4), the Microsoft Entra ID identity boundary (Volume III §5), the Microsoft.KeyVault HSM customer-managed key (Volume III §4.4), and the Microsoft Purview audit graph (Volume II §10). If a client-facing artifact derived from these volumes erodes any of those boundaries, the deployment posture has slipped before the words have. Restate the boundaries and rebuild the artifact.
