# APEX Core · v1.2 Amendment
## Schema Versioning Manifest

**Amendment version:** 1.2
**Supersedes:** Nothing; additive to Core v1.1
**Effective:** 2026-04-17
**Downstream impact:** All active editions (RC, TH, HLS, TMT, ER, ICE) update their Part 0 inheritance declaration to reference `apex-core v1.2` and add a pointer to their new `schemas.manifest.json`. No existing edition content is invalidated.

---

## Rationale

APEX editions define 3-5 canonical schemas each (MERML, SCML, CXML, MKTL in RC; HOSML, REVML in TH; and so on). These schemas are the data grammar that agents and orchestrations contract against. When a schema changes - an entity is added, a grain is refined, a column is deprecated - consumers need three things: a stable version number that agents and ORCH contracts can pin against, a machine-readable record of what actually changed between two versions at entity granularity, and a view of what is deployed where across the client fleet.

Today none of these exist as first-class artifacts. Schema changes propagate by PR review and tribal memory. This amendment closes that gap using the same inheritance model Core v1.1 established for the edition registry: Core owns the contract, editions own the content, a new fleet layer records deployment state, and a validation tool surfaces the whole picture.

This amendment is additive. No existing edition's content is invalidated.

---

## 1. New L1 Artifact

**File:** `apex-core/data/schema-manifest-contract.json`

This JSON file is the normative contract that every downstream `schemas.manifest.json` must conform to. It defines the required top-level fields, the `schema_entry`, `entity_entry`, `change_entry`, and `change_delta` templates, the SemVer decision table, and the anti-cheating rules. It is versioned with Core (this initial release is `contract_version: "1.0"` under `core_version: "1.2"`).

The convention governing required-vs-optional defaults for fields in this contract is stated in `apex-core/conventions/schema-versioning.md`. See that document for the normative rule.

---

## 2. New Convention Document

**File:** `apex-core/conventions/schema-versioning.md`

A one-page normative reference covering: the four-layer manifest model (L1/L2/L3/L4), the SemVer decision table, the anti-cheating rules, the required/optional default convention for the L1 contract, and pointers to this amendment and the source design document.

---

## 3. Part 11 Acceptance Criteria Additions

Three new criteria extend Core Part 11. Every edition claiming Core v1.2 inheritance must satisfy all three:

- Edition includes `schemas.manifest.json` conforming to Core v1.2 contract.
- Every schema declares `version` + `changelog` + `envelope_required`.
- `apex-validate` exits `0` or `1` (no criticals) against the edition.

These are additive; the existing 13 Core Part 11 criteria are unchanged.

---

## 4. New Core Tools

Two tools are introduced as Core-shipped artifacts. The existing Phase 4 validation harness (`validate-edition.js`, `validate-registry.js`) is extended, not replaced.

| Tool | File | Purpose |
|---|---|---|
| **`apex-validate`** | `apex-core/tools/apex-validate.js` | Dual-mode validator (author mode + fleet mode). Writes `report.html` (APEX design-system-styled) and `report.json` on every run. Exits `0` clean, `1` warnings only, `2` criticals present, `3` contract or manifest shape broken. |
| **`apex-sync`** | `apex-core/tools/apex-sync.js` | Tenant-side CLI. Compares `deployed-manifest.json` against the pinned manifest and applies DDL per the account's `auto_upgrade_policy`. Commands: `status`, `check`, `plan`, `apply`, `rollback`. |

Full CLI reference and runtime sequence are in Parts 6 and 7 of the source design document.

---

## 5. New Fleet Layer

`apex-fleet/` is introduced as a new Deloitte-side operational folder (separate repo or subfolder, at SteerCo discretion). Contents:

- `apex-fleet/data/fleet-registry.json` - L3 source of truth for per-account pinned schema versions and upgrade policy.
- `apex-fleet/tools/release-bundler.js` - assembles signed per-account manifest bundles from L2 + L3.
- `apex-fleet/dashboards/fleet-report.html` - generated by `apex-validate --fleet`.

Fleet state is explicitly a Deloitte operational concern, not an edition-authoring concern. Keeping it in its own layer prevents client onboarding churn from polluting edition spec history. The tenant-side L4 file (`<client-onelake>/apex-sync/deployed-manifest.json`) never leaves the tenant; only opaque account ID, pinned versions, and manifest hash cross the boundary on heartbeat.

---

## 6. Downstream Spec Updates Required

Every active edition spec (RC, TH, HLS, TMT, ER, ICE) updates its Part 0 Inheritance Declaration line:

**Before:**
> This spec inherits from APEX Core v1.1.

**After:**
> This spec inherits from APEX Core v1.2.

And adds a pointer to the edition's new manifest:

> **Schema manifest:** `apex-<code>/data/schemas.manifest.json` - conforms to Core v1.2 L1 contract.

This is a two-line change per edition spec. The new `schemas.manifest.json` file is populated from each edition's existing `schemas.json` and adopted at each edition's pace; the file is optional until the edition elects to adopt v1.2.

---

## 7. Handoff Notes

This amendment is additive. No existing APEX content is invalidated. An edition that has not yet written an L2 manifest is still a valid APEX edition under Core v1.1; adopting v1.2 is a two-line spec change plus one new JSON file.

The build sequence is documented in Part 10 of the source design document and tracked as Phases 1-4 of the implementation plan. Phase 1 (this amendment, the L1 contract, the convention doc, and the CHANGELOG entry) is independently valuable and mergeable.
